# Bug 74: `parse_game_response` can hallucinate a room with no support in the raw text

**Status:** Fixed

Observed live (`logs/watch_20260708_160703.json`, entry 17): action
`INVENTORY`, raw response `"You own nothing at all!"` — nothing else. The
model reported `room: "pearl room"` and `notable_events: ["I have just
died and been taken to the pearl room. Everything I was carrying was lost
at the location where I died."]`. None of that is in the response. The
model saw a sparse result ("own nothing"), recognized it matched the
shape of the "Death and the pearl room" section of its own system prompt
(`docs/agent_behavior_spec.md`), and fabricated a narrative to explain it
— using phrasing that echoes the spec's own wording — then reported the
fabrication as an extracted fact.

`state["current_room"]` genuinely got set to `"pearl room"` for one step.
The very next `LOOK` happened to correctly re-establish `"huge pile of
garbage"`, so this self-corrected by luck (`LOOK` is always a safe
recovery move regardless of why it was issued) rather than by anything
that actually caught the error.

Not the same failure as the earlier `"null"`-string/`"buried"` cases
(agent_tools.py's `_NULL_LIKE_ROOM_VALUES` guard and the tightened `room`
field description) — `"pearl room"` is a real, valid room name in this
game, so a sentinel-value check can't distinguish "correctly identified"
from "invented a dramatic explanation for sparse data."

**Fix:** Replaced the `room` field with `room_quote` — required to be a
verbatim substring of the actual response text, not a room name the model
constructs. The host verifies the quote is literally present
(case-insensitive) before trusting it at all; only a grounded quote gets
passed to `agent._resolve_room_name` for canonicalization (the same
article/preposition-stripping and fuzzy-matching it already does for the
legacy path — no new matching logic needed, just a guaranteed-grounded
input instead of a trusted one). An ungrounded or missing quote is treated
as no room reported for that step (matches how a terse response with
nothing to extract already behaves) — no retry-the-parse loop, since a
bounded retry against a model that's already fabricating is just a new way
to get stuck. A rejected claim is logged as a low-severity
`room_not_grounded` finding via the same `request_capability`-shaped
pipeline, for visibility rather than automatic action.

**How we know it worked:** replaying entry 17's exact input
(`room_quote` absent/ungrounded against `"You own nothing at all!"`)
against the fixed code leaves `state["current_room"]` unchanged instead of
corrupting it to `"pearl room"`.
