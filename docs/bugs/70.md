# Bug 70: Failed `take` abandons inspection even when the object is worth examining

**Status:** Fixed

Reported after watching a real run: the agent tried `take flagpole`, got
`"That's too heavy."`, and never issued `examine flagpole` afterward —
despite `examine flagpole` being exactly how bug 31 ("Sub-objects revealed
by examine not extracted") was originally found (it reveals a halyard
fastened to the flagpole). Confirmed in several saved logs, e.g.
`logs/watch_20260701_083519.json` step 5 (`take flagpole` → `"That's too
heavy."`) is immediately followed by other actions with no further
`flagpole` inspection, whereas an older log from before this regression
(`logs/watch_20260630_220033.json` step 5) shows the same failure followed
by `examine`/`read`/`look inside flagpole` as expected.

This isn't the same as **bug 58** (scenery items skip inspection), though
it's the same code path. Bug 58 intentionally makes a *true* scenery item
(`"That's probably just scenery."`) skip the remaining inspection verbs —
correct, since scenery has nothing more to reveal and running `examine`
etc. on it just wastes steps. The regression here is that `take`'s failure
handling in `process_agent_step` (agent.py) clears
`state["current_inspection"]` on **every** `take` failure — hard, soft, or
unrecognized — not just the scenery case:

```python
if insp_verb == "take" and effective_target:
    if _is_soft_failure(response):
        ...
        state["current_inspection"]["target"] = None
    elif _is_hard_failure(response):
        ...
        state["current_inspection"]["target"] = None
    else:
        ...  # unrecognized failure (see bug/PR #72's classify_failure_patterns work)
        state["current_inspection"]["target"] = None
```

`"That's too heavy."` isn't in `hard_failure_patterns` or
`soft_failure_patterns` in `configs/knight_orc.json` at all, so it falls
into the third (`unrecognized_failure`) branch added by PR #72 — which
also clears inspection. `tests/test_agent.py::
test_take_unrecognized_response_triggers_recheck_not_succeeded` asserts
this clearing is current, intentional behavior (`assert
state["current_inspection"]["target"] is None`), so this is a real gap in
the design, not a one-off regression in that PR.

The flagpole is a legitimate, examine-worthy object — it's simply too
heavy to carry, not scenery — so clearing the whole inspection sequence
means the agent never runs `examine flagpole` and never discovers the
halyard fastened to it. The same applies to anything else that's fixed in
place or otherwise permanently un-takeable but still interactive (a locked
door, a mounted weapon, etc.).

**Fix:** Told the two cases apart instead of clearing inspection on any
`take` failure:

- Added a new `scenery_patterns` config field (`game_config.py`,
  `configs/knight_orc.json`, `schemas/game_config.schema.json`), compiled to
  `config.scenery_pattern`, and a matching `_is_scenery_response()` helper
  in `agent.py`. Default/real value: `"probably just scenery"` — the same
  phrase bug 58 added to `hard_failure_patterns` (which it stays in, for
  the separate "record take as permanently invalid" classification).
- `process_agent_step`'s `take`-failure handling now only clears
  `state["current_inspection"]` when the response is scenery-patterned,
  regardless of *which* of the three branches (soft/hard/unrecognized
  failure) it came from — a failed take by itself no longer abandons the
  object. A successful take is unaffected (never cleared inspection).
- Classified `"too heavy"` into `soft_failure_patterns` in
  `configs/knight_orc.json` (state-dependent — if Knight Orc's weight limit
  turns out to be inventory-total rather than per-object, this stays
  retryable rather than permanently blacklisting the object; it was
  previously falling into the generic `unrecognized_failure` bucket, which
  still works too since that path no longer clears inspection either, but
  classifying it avoids a redundant future `take` attempt on revisit).

**How we know it worked:** New/updated coverage in `tests/test_agent.py`:
`TestIsSceneryResponse` (4 tests) for the new helper; `test_take_hard_failure_records_invalid_keeps_inspecting`
(was `..._and_clears_inspection` — inverted, since "You can't take that."
isn't scenery) and `test_take_failure_then_next_action_is_examine_not_abandoned`
(end-to-end: take fails → next decision is `examine`, not abandonment);
`test_take_soft_failure_records_blocked_not_invalid` and
`test_take_unrecognized_response_triggers_recheck_not_succeeded` updated to
assert inspection continues rather than clears. `test_take_scenery_clears_inspection`
(bug 58) still passes unchanged — genuine scenery still skips inspection.
`python -m pytest tests/ -q --ignore=tests/test_evals.py` — 354 passed, 2
xfailed. Behaviorally, a live rerun through the flagpole scene (the
"dismal fairground in a rowan coppice" room) should show `take flagpole` →
`"That's too heavy."` → `examine flagpole` → `"...Fastened to it is a
halyard."` in the step log, with `halyard` then appearing as a new
`uninspected_objects` entry — not `take flagpole` followed immediately by
movement or another object.

**Aside — a latent test-isolation issue this surfaced:** `scripts/watch_run.py`
deliberately loads `configs/knight_orc.json` onto the shared `game_config.config`
singleton at import time (so it applies whether run directly or imported).
`tests/test_issue27.py` imports `scripts.watch_run` transitively, so any
full test-suite run (which collects/imports every test file) picks up the
real on-disk config instead of `GameConfig()`'s bare Python defaults for
tests that never call `load_from_file` themselves. This had never mattered
before because nothing in the real config collided with a phrase a test
relied on being unclassified — until `"too heavy"` was added here, which
broke `test_take_unrecognized_response_triggers_recheck_not_succeeded`
(full-suite-only failure, passed in isolation). Fixed by making that test
use a synthetic nonsense phrase instead of real game text for its
"genuinely unrecognized" example, decoupling it from whatever the ambient
config happens to classify at any given time. Not otherwise addressed here
— worth a dedicated bug if this bites again.
