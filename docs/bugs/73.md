# Bug 73: Inconsistent action casing from the tool-calling model can mask loop detection and fragment entity history

**Status:** Open

Observed in a live 10-step tool-calling run
(`logs/watch_20260708_160517.json`): the model sends commands with
inconsistent casing — `LOOK` and `look`, `DODGE`, `EXAMINE putty knife`
alongside `examine putty knife` — with no pattern to which it picks.

Not a game-correctness problem: responses to both `LOOK` and `look` came
back as normal room descriptions, so the interpreter clearly doesn't care
about case (typical for this genre). The risk is entirely in the host's
own bookkeeping, which does case-sensitive exact-string comparisons in two
places:

1. **Loop detection** (`agent._detect_loop`, used by both the legacy and
   tool-calling paths) counts exact-match repeats of `entry["action"]`
   against a threshold (8 in a 10-step window). A model alternating
   `"look"`/`"LOOK"` while genuinely stuck would have each variant counted
   separately — staying under the threshold on either spelling alone while
   comfortably over it combined — and the loop would go undetected.
2. **Entity history** (`parse_strategies.apply_parse_result`,
   `agent._record_verb_outcome` — `agent_tools.py::_apply_parse_game_response`
   at the time this bug was filed has since been replaced by the shared
   `apply_parse_result`, same mechanism) stores objects into
   `state["known_entities"]` keyed by the object name exactly as it
   appeared in the executed command. Verb casing is already handled
   (`parse_strategies.split_verb_object` lowercases the whole command
   before matching, confirmed working: `examine putty knife` then
   `EXAMINE putty knife` in the observed run correctly classified the
   second as `redundant`) — but if the *object* portion's casing varied
   between two attempts (`examine putty knife` vs `examine Putty Knife`),
   those would fragment into two separate dict keys, and
   `query_entity_history` would never find the earlier one. Not observed
   in this run (object casing happened to stay consistent), but the
   mechanism has no guard against it — directly relevant to the DeepSeek
   repeat-thrashing already tracked in memory
   `project-deepseek-thrash-mitigation`, and could compound it on a
   longer run.

**Confirmed at scale** in a live 100-step DeepSeek run
(`logs/watch_20260709_144142.json`): `loop_detected` never fired once
across all 100 steps, despite obvious thrashing — `examine putty knife`
(14 exact-string occurrences, 16 once case-folded), `examine pile of
garbage` (8 exact, 12 case-folded), `LOOK`/`look` (26 + 5 = 31
case-folded) all split across casing variants, none individually crossing
`_detect_loop`'s threshold within its 10-step window even though the
case-folded totals plainly should have. This is exactly the failure mode
predicted above, now reproduced on a real run rather than just reasoned
about from a shorter one — the agent spent a large fraction of a 100-step
budget stuck re-examining the same 2-3 objects in the same room.

**Proposed fix:** normalize case at the comparison/storage layer, not at
what's actually sent to the game (`execute_game_command`'s `command` should
stay whatever the model wrote, since the interpreter doesn't care and
changing it risks losing intentional capitalization in proper nouns).
Concretely: case-fold `entry["action"]` before comparison in
`agent._detect_loop`, and case-fold the object key (not the display value)
used for `state["known_entities"]` lookups/storage in
`parse_strategies.apply_parse_result`/`agent._record_verb_outcome`.

**Effort: Low | Risk: Low**
