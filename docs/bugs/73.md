# Bug 73: Inconsistent action casing from the tool-calling model can mask loop detection and fragment entity history

**Status:** Open — scope expanded, see Finding 3 and the Implementation Plan below

Observed in a live 10-step tool-calling run
(`logs/watch_20260708_160517.json`): the model sends commands with
inconsistent casing — `LOOK` and `look`, `DODGE`, `EXAMINE putty knife`
alongside `examine putty knife` — with no pattern to which it picks.

Not a game-correctness problem: responses to both `LOOK` and `look` came
back as normal room descriptions, so the interpreter clearly doesn't care
about case (typical for this genre). The risk is entirely in the host's
own bookkeeping, which does case-sensitive exact-string comparisons in two
places:

1. **Loop detection** (`agent._detect_loop`, used by both the legacy and
   tool-calling paths) counts exact-match repeats of `entry["action"]`
   against a threshold (8 in a 10-step window). A model alternating
   `"look"`/`"LOOK"` while genuinely stuck would have each variant counted
   separately — staying under the threshold on either spelling alone while
   comfortably over it combined — and the loop would go undetected.
2. **Entity history** (`parse_strategies.apply_parse_result`,
   `agent._record_verb_outcome` — `agent_tools.py::_apply_parse_game_response`
   at the time this bug was filed has since been replaced by the shared
   `apply_parse_result`, same mechanism) stores objects into
   `state["known_entities"]` keyed by the object name exactly as it
   appeared in the executed command. Verb casing is already handled
   (`parse_strategies.split_verb_object` lowercases the whole command
   before matching, confirmed working: `examine putty knife` then
   `EXAMINE putty knife` in the observed run correctly classified the
   second as `redundant`) — but if the *object* portion's casing varied
   between two attempts (`examine putty knife` vs `examine Putty Knife`),
   those would fragment into two separate dict keys, and
   `query_entity_history` would never find the earlier one. Not observed
   in this run (object casing happened to stay consistent), but the
   mechanism has no guard against it — directly relevant to the DeepSeek
   repeat-thrashing already tracked in memory
   `project-deepseek-thrash-mitigation`, and could compound it on a
   longer run.
3. **Direction/graph-edge bookkeeping** — found while implementing the fix
   above, not in the original run. `world_graph.update_graph` uses the raw
   `action` argument (not case-folded) in `REVERSE.get(action, "")`; a
   capitalized direction (`"WEST"`) makes this a silent miss, which skips
   reverse-edge wiring and `Unknown (...)` placeholder cleanup for that
   step entirely. The same case-sensitive `DIRECTIONS`/`REVERSE` mistake is
   repeated at four more call sites: `agent._detect_loop`'s own
   "exclude productive moves" exemption (line 51 — this one is actually
   *backwards*: a genuinely productive capitalized move gets counted toward
   the repeat threshold instead of being exempted), `agent.determine_next_action`'s
   anti-oscillation check and direction-diversity scoring (lines 143-144,
   155-158), `agent.process_agent_step`'s futile-edge-marking gate (line
   378), `agent_tools.py`'s equivalent gate (line 410), and
   `parse_strategies/base.py`'s position-lost-detection branch (line 230).
   Room names need no equivalent fix — `world_graph.resolve_room_name`
   already normalizes both sides of every comparison via `normalize_room`,
   so there is no raw-key-equality path for rooms to begin with.

**Confirmed at scale** in a live 100-step DeepSeek run
(`logs/watch_20260709_144142.json`): `loop_detected` never fired once
across all 100 steps, despite obvious thrashing — `examine putty knife`
(14 exact-string occurrences, 16 once case-folded), `examine pile of
garbage` (8 exact, 12 case-folded), `LOOK`/`look` (26 + 5 = 31
case-folded) all split across casing variants, none individually crossing
`_detect_loop`'s threshold within its 10-step window even though the
case-folded totals plainly should have. This is exactly the failure mode
predicted above, now reproduced on a real run rather than just reasoned
about from a shorter one — the agent spent a large fraction of a 100-step
budget stuck re-examining the same 2-3 objects in the same room.

**Proposed fix:** normalize case at the comparison/storage layer, not at
what's actually sent to the game (`execute_game_command`'s `command` should
stay whatever the model wrote, since the interpreter doesn't care and
changing it risks losing intentional capitalization in proper nouns). See
the **Implementation Plan** section below for the full design: a shared
`world_graph.normalize_direction()` helper for every `DIRECTIONS`/`REVERSE`
site (including the `update_graph` bug), plain `.lower()` folding in
`agent._detect_loop`'s repeat-counting, and a new
`parse_strategies.resolve_entity_key()` helper (mirroring
`world_graph.resolve_room_name`'s pattern) for every `known_entities`/
`known_npcs` lookup/storage site.

**Effort: Medium | Risk: Low** — reassessed after scope expansion; still
low risk (every change is comparison/storage-layer only, well-covered by
existing test patterns), but more call sites across more files than
originally scoped.

## Implementation Plan

This plan is written for Copilot to implement. It was designed by a
planning pass and verified line-by-line against the current code
(`world_graph.py`, `agent.py`, `parse_strategies/base.py`,
`agent_tools.py`) before being finalized here.

### 1. `world_graph.normalize_direction()` — new shared helper

Add near `DIRECTION_NORMALIZE` (`world_graph.py:51`):

```python
def normalize_direction(word):
    """Lowercase and expand a full compass-word alias to the abbreviated
    form (see DIRECTION_NORMALIZE). Comparison/storage-layer only — never
    apply this to what's sent to the game via execute_game_command."""
    word = word.strip().lower()
    return DIRECTION_NORMALIZE.get(word, word)
```

This generalizes the pattern `parse_strategies/deterministic.py:117` (and
`resolve_room_name:129`) already apply inline correctly.

### 2. Fix `update_graph`'s action-casing bug (`world_graph.py:144-178`)

Normalize `action` once at the top, use `normalized_action` everywhere
`action` is currently used for `REVERSE.get`/placeholder names/edge label:

```python
    exits = [normalize_direction(d) for d in exits]
    if room_name not in graph:
        graph.add_node(room_name)

    normalized_action = normalize_direction(action) if action else ""
    reverse_action = REVERSE.get(normalized_action, "")
    if previous_room and previous_room != room_name and reverse_action:
        for placeholder in (
            f"Unknown ({normalized_action} from {previous_room})",
            f"Unknown ({reverse_action} from {room_name})",
        ):
            if graph.has_node(placeholder):
                graph.remove_node(placeholder)
        existing_labels = {
            d.get("label")
            for d in (graph.get_edge_data(previous_room, room_name) or {}).values()
        }
        if normalized_action not in existing_labels:
            graph.add_edge(previous_room, room_name, label=normalized_action)
```

Verified safe for non-direction actions (e.g. `"take putty knife"`):
`normalize_direction` just lowercases it, `REVERSE.get` returns `""`,
`reverse_action` is falsy, the whole block no-ops exactly as today — every
use of `action` in this function is gated behind `reverse_action` being
truthy first. Storing the *normalized* label (not the model's raw casing)
is safe because a stored edge is host bookkeeping, not something sent to
the game yet — when it's later read back by `nav_command`/
`get_next_move_to_target`, handing the interpreter a lowercase word is
already proven fine (the reproduction run above showed `LOOK` and `look`
both returned normal responses — the interpreter is case-blind).

Also update `mark_edge_futile` (`world_graph.py:210`) to normalize
internally so callers can pass raw model text safely:

```python
def mark_edge_futile(state, from_room, direction):
    direction = normalize_direction(direction)
    ...
```

### 4. Case-insensitive `known_entities`/`known_npcs` keying

New helper in `parse_strategies/base.py` (same conceptual home as
`apply_parse_result`, and where nearly every call site already lives),
mirroring `world_graph.resolve_room_name`'s normalize-then-linear-scan,
first-casing-wins pattern:

```python
def resolve_entity_key(entities, name):
    """Return the key `entities` should be looked up/stored under: an
    existing case-insensitive match if present (preserving its original
    casing), else `name` unchanged. Mirrors world_graph.resolve_room_name's
    pattern for dict keys instead of graph nodes."""
    if name in entities:
        return name
    lowered = name.lower()
    for existing in entities:
        if existing.lower() == lowered:
            return existing
    return name


def _case_insensitive_member(name, items):
    """Case-insensitive membership check for a plain list (inventory,
    uninspected_objects)."""
    lowered = name.lower()
    return any(item.lower() == lowered for item in items)
```

Export both from `parse_strategies/__init__.py` alongside `apply_parse_result`.

Call sites to update, all in `parse_strategies/base.py::apply_parse_result`
unless noted:

- **`agent._record_verb_outcome`** (`agent.py:32-37`) — the single choke
  point used by both `process_agent_step` and `apply_parse_result`. Resolve
  the key first and return it, so callers that immediately re-look-up the
  entity use the same resolved key:
  ```python
  def _record_verb_outcome(state, target, verb, outcome):
      target = parse_strategies.resolve_entity_key(state["known_entities"], target)
      entity = state["known_entities"].setdefault(
          target, {"status": "discovered", "location": state["current_room"], "verb_outcomes": {}}
      )
      entity.setdefault("verb_outcomes", {})[verb] = outcome
      return target
  ```
  (`agent.py` already does `import parse_strategies` at module scope.)
- **Line ~143** (`entity = state["known_entities"].get(obj)` right after
  `_record_verb_outcome`): capture the returned key —
  `obj = agent._record_verb_outcome(state, obj, verb, outcome)` then
  `entity = state["known_entities"].get(obj)`.
- **Gift receipt loop** (~line 197-205): resolve `item`'s key before the
  `not in state["inventory"]` check (use `_case_insensitive_member`) and
  before the `known_entities` get/set.
- **NPC discovery loop** (~line 267-269): resolve via `resolve_entity_key`
  against `state["known_npcs"]` before `setdefault`.
- **Object/creature-reclassification loop** (~line 271-284): resolve both
  the `known_npcs` check and the `known_entities` check/set via
  `resolve_entity_key`; use `_case_insensitive_member` for the
  `uninspected_objects`/`inventory` "already pending or held" check.
  `state["uninspected_objects"].append(obj_name)` still appends the *raw*
  display casing — that becomes a future `take {obj_name}` command, never
  normalized.
- **Gained-items loop** (~line 300-307) and **inventory reconciliation**
  (~line 340-357, the `action_taken == "inventory"` block): same
  `resolve_entity_key`/`_case_insensitive_member` treatment on both the
  downgrade and upgrade passes.
- **`agent_tools.py::_impl_query_entity_history`** (line 220-225) — this is
  the exact tool call the model uses to check prior history; it must
  resolve the key the same way:
  ```python
  def _impl_query_entity_history(state, object_name):
      entity_key = parse_strategies.resolve_entity_key(state["known_entities"], object_name)
      entity = state["known_entities"].get(entity_key, {})
      return {"verb_outcomes": entity.get("verb_outcomes", {}), "last_result_summary": entity.get("last_result_summary")}
  ```
- **`pre_verb_outcomes` reads** in `agent.py:280-283` and
  `agent_tools.py:386-389` — both currently do a raw `.get(effective_target, {})`;
  resolve the key first via `resolve_entity_key` before the `.get`.
- **`determine_next_action`'s uninspected-objects pop** (`agent.py:119-121`)
  — needs a fix, not naturally covered: `known_entities` can be pre-seeded
  cross-run from the strategy sidecar (feature 64) under a different casing
  than this run's extraction produces. Concretely: sidecar has
  `known_entities["Putty Knife"]`; this run's object loop sees
  `"putty knife"` (resolves fine via `resolve_entity_key`, updates the
  existing entry) but still appends the *raw* `"putty knife"` to
  `uninspected_objects`. When popped later, `state["known_entities"].get("putty knife")`
  misses the `"Putty Knife"` key, silently losing cross-run `verb_outcomes`
  (e.g. a prior `"read": "invalid"`) — reproducing exactly the
  repeat-invalid-verb failure mode this bug describes. Fix:
  ```python
  if state["uninspected_objects"]:
      new_target = state["uninspected_objects"].pop(0)
      entity_key = parse_strategies.resolve_entity_key(state["known_entities"], new_target)
      entity_data = state["known_entities"].get(entity_key, {})
      verb_outcomes = entity_data.get("verb_outcomes", {})
      ...
      inspection["target"] = new_target   # raw casing preserved — becomes the actual `take` command
  ```

No other call site needs touching — the theft-removal and gift-removal
loops in `apply_parse_result` already do case-insensitive `.lower()`
comparisons for *removal*, only *insertion/lookup* sites needed the fix.

### Test plan

All new tests fit `tests/test_agent.py`'s existing style (no dedicated
`tests/test_world_graph.py` — stay consistent with current convention).

- `world_graph.normalize_direction`: lowercases; expands a full-word alias
  (`"Northeast"` → `"ne"`); leaves a non-direction string just lowercased.
- `update_graph` repro: an uppercase `"WEST"` action still wires the
  reverse edge and cleans up the `Unknown (...)` placeholder, and the
  stored edge label is the normalized `"west"`, not raw `"WEST"`.
- `_detect_loop` repro mirroring the real log (`logs/watch_20260709_144142.json`
  showed `examine putty knife` x14 + `EXAMINE putty knife` x2, and
  `LOOK` x26 / `look` x5): construct a game_log where each casing variant
  alone is under threshold but folded-together is over it; assert
  `_detect_loop` now fires. Also a regression test that an uppercase,
  room-changing direction is still exempted as a productive move.
- `TestResolveEntityKey`: exact match returns same key; case-insensitive
  match returns the existing (earlier) key; no match returns name
  unchanged.
- Integration test: record a verb outcome under one casing, then look it
  up under a different casing (`_record_verb_outcome`, and separately
  `agent_tools._impl_query_entity_history`) — assert no fragmentation and
  history is found. Same for `known_npcs`.
- Regression test for the cross-run pre-seed pop (§4 above,
  `determine_next_action`): pre-seed `known_entities["Putty Knife"]` with a
  `"read": "invalid"` outcome, seed `uninspected_objects = ["putty knife"]`,
  call `determine_next_action`, assert `"read"` is excluded from the
  resulting inspection sequence.

### How will we know it worked?

Beyond unit tests (which prove each mechanism in isolation), validate with
a live `scripts/watch_run.py` run against the tool-calling backend
(≥100 steps, matching the scale of the reference log), then check:

1. **Loop detection fires on casing-mixed thrashing** — grep the new run's
   log for any action (case-folded) whose combined count across casing
   variants in a 10-step window is ≥ 8; confirm `loop_detected` actually
   appears (it never did, even once, in the pre-fix reference run).
2. **No orphaned `Unknown (... from ...)` placeholders survive a
   same-direction return trip regardless of casing** — inspect the saved
   graph for any `Unknown` node whose direction reverses an already-confirmed
   edge; there should be none, even when the original move was capitalized.
3. **`known_entities`/`known_npcs` entry counts match distinct
   case-insensitive names actually mentioned** — compare dict size against
   the count of distinct (case-folded) object/NPC names across the run's
   `extracted.objects`/`extracted.npcs`; previously casing drift would
   silently inflate the dict.
4. **`query_entity_history` returns non-empty `verb_outcomes` for an object
   examined earlier under different casing** — find at least one such case
   in the tool-call trace and confirm the returned data isn't empty.
