# Bug 61: Streamlit UI ignores LLM_PROVIDER and crashes attempting local model load

**Status:** Open

When `LLM_PROVIDER=deepseek` (or any cloud provider) is set in `.env`, the Streamlit UI still attempts to load a local llama.cpp model. This causes a hard crash via `GGML_ASSERT(i1 >= 0 && i1 < ne1) failed` in the native tensor library, killing the process with SIGABRT before the UI becomes usable.

The headless `watch_run.py` path correctly reads `LLM_PROVIDER` from `.env` and uses the cloud adapter. The Streamlit `app.py` / `llm.py` cache path does not.

**Error observed:**
```
/tmp/pip-install-.../llama.cpp/ggml/src/ggml-cpu/ops.cpp:5051:
GGML_ASSERT(i1 >= 0 && i1 < ne1) failed
...
Unable to attach: program terminated with signal SIGABRT, Aborted.
```

**Likely cause:** `app.py` initialises the LLM via `@st.cache_resource` without checking `LLM_PROVIDER`; it unconditionally calls the llama.cpp loader. The cloud provider path added in feature 34 was only wired up in `watch_run.py`, not in the Streamlit session initialisation.

**To fix:**
- In `app.py` (or `llm.py`), read `LLM_PROVIDER` before deciding which loader to call
- When `LLM_PROVIDER != "local"`, call `load_cloud_llm(provider, model, api_key)` instead of the llama.cpp loader
- The sidebar model-path field should be hidden / replaced with provider/model/key fields when in cloud mode

**How will we know it's fixed?**
- With `LLM_PROVIDER=deepseek` in `.env`, `./run_app.sh` loads the Streamlit UI without any crash
- No llama.cpp model path is shown or required in the sidebar
- The auto-run loop produces step log entries using the cloud LLM
- Switching back to `LLM_PROVIDER=local` still works with a local model path
