# Bug 69: Agent loops forever on a `run to X` the game's nav command rejects

**Status:** Fixed

Found by `scripts/detect_anomalies.py` on a real run
(`logs/watch_20260704_224041.json`): the agent had an `active_goal` whose
room, `huge pile of garbage`, was in `visited_rooms`, so `_nav_command()`
kept emitting the fast-nav template `run to huge pile of garbage` every
step. The game's native nav parser doesn't recognize that particular
room's full descriptive name and rejected it every time with `"I don't
know where that could be!"` — but nothing recorded that rejection, so the
agent re-issued the identical command 8 steps in a row until the loop
detector killed the run.

```
[ 17/50] run to huge pile of garbage  trampled field
[ 18/50] run to huge pile of garbage  trampled field
...
[ 24/50] run to huge pile of garbage  trampled field  ✗ LOOP
Outcome: agent_failure
```

`process_agent_step()` already clears `active_goal` on a hard-failed
`go to`/`run to` (so the anomaly isn't immediately re-queued), but with
nothing else remembering the rejection, the *next* time this room became a
navigation target — from a different anomaly, a different unresolved goal,
or the same one rediscovered — `_nav_command()` had no reason not to try
the exact same rejected template again.

**Fix:**
- `agent.py`'s `_nav_command()` now also checks a `nav_blacklist` state set
  before using the fast/full nav template; a blacklisted target falls back
  to graph-based step navigation instead:
  ```python
  if (template and target in state.get("visited_rooms", set())
          and target not in state.get("nav_blacklist", set())):
      return template.format(target=target)
  return get_next_move_to_target(state, target)
  ```
- `process_agent_step()` adds the target to `state["nav_blacklist"]` at the
  same point it already clears `active_goal` on a hard-failed `go to`/`run
  to`, so the rejection is remembered for the rest of the run (not just
  until the anomaly is re-queued).

**How we know it worked:** Added `tests/test_agent.py` coverage that didn't
exist before this fix:
- `TestNavCommand::test_blacklisted_target_falls_back_to_graph_even_if_visited`
  / `test_non_blacklisted_target_still_uses_fast_template` — `_nav_command()`
  skips the template only for blacklisted targets.
- `TestNavBlacklistMarkedOnStep` (three tests) — a hard-failed `run to`
  populates `nav_blacklist` and clears `active_goal`; a successful `run to`
  does not; a target already in `nav_blacklist` is bypassed on the very
  next step (asserts the real command sent is the graph-based `"north"`,
  not another rejected `run to`).

`python -m pytest tests/ -x -q --ignore=tests/test_evals.py` passes (349
passed, 2 xfailed — up from 344, the 5 new tests above). Behaviorally, a
future run hitting the same room-name rejection should show at most one
`run to <room>` attempt against that target before falling back to
single-step directional movement (`north`, `east`, etc.) for the rest of
the run, instead of repeating the identical rejected command until the
loop detector fires.
