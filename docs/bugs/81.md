# Bug 81: Tool-calling model hallucinates an object name and sends it as a live game command

**Status:** Fixed

Found while re-examining the same run documented in bug 80
(`logs/knight_orc_run_20260709_2242.json`) — the same 14-step GUI session
against a cloud tool-calling model. This is a different mechanism from
bug 80's alternation-detector gap, so it's filed separately, though both
came from the same degraded episode.

At step 9, `examine putty knife` returned: *"It is rusty and blunt,
barely able to carve slime off a puddle."* At step 10, the model called
`execute_game_command` with `"examine sword"`, stating its own reason
as: *"The game just described a rusty, blunt sword — I should examine it
properly."*

There is no sword anywhere in this scenario — `objects` at every point in
this sequence was only ever `["putty knife", "hooded cloak"]` (confirmed
by re-reading the full `extracted` field for every step in this room).
The model took the putty knife's own description ("rusty and blunt") and
misattributed it to an invented object it decided to call "sword," then
issued a real command against the live game for that nonexistent object.
The game engine rejected it (*"the word 'sword' is not needed to finish
this part of the game"*), so no state corruption resulted, but a turn was
wasted and — more importantly — this is a case of the tool-calling decide
loop sending an **ungrounded, hallucinated target** to
`execute_game_command`, not just a misclassified extraction field.

**Root cause (mechanism, not yet a full fix design):** `execute_game_command`'s
`command` field (`agent_tools.py:115-125`, `TOOL_SCHEMAS`) is an
unconstrained free-text string — the tool schema places no validation on
it, and `_dispatch_tool`/`_run_decide_loop` pass whatever the model
supplies straight to `game_engine.execute_game_command` with no check
against `known_entities`, the current room's extracted `objects`, or any
other ground-truth object list. This is the same *category* of gap bug
77 closed for **extraction** fields (`objects`/`npcs` grounded against
the raw response text) and bug 78 closed for **room naming**
(`room_quote` grounded as a verbatim substring) — but neither of those
fixes touches the tool-calling loop's own **action selection**, which
remains fully ungrounded. A model can ask the game to interact with
literally anything it imagines, not just misreport what it saw.

**Relationship to bug 80:** bug 80 is about the anomaly-detector layer
being structurally unable to flag the *alternation* this episode also
exhibits (streak-only detection logic). This bug is about a distinct,
earlier-in-the-pipeline problem — the decide loop itself producing an
ungrounded command in the first place. Fixing bug 80's detectors would
make a *future* recurrence of this kind of episode more likely to be
flagged after the fact; it would not stop the hallucinated command from
being sent. The two are complementary, not duplicates.

**Proposed fix directions (not yet designed):**
1. Ground `execute_game_command`'s target the same way bug 77 grounds
   extraction: before dispatch, if the command references an object name
   (e.g. via a lightweight `examine|take|read|...` + noun-phrase parse),
   check it against `state["known_entities"]`/the current room's last
   known `objects` list, and either reject/re-prompt the model
   ("`sword` isn't a known object here — did you mean `putty knife`?")
   or at minimum flag it (`notable_events`/a new anomaly type) so it's
   visible without silently letting it through to the game engine.
2. Alternatively (lighter-weight, no command-parsing needed): log every
   `execute_game_command` call whose target string doesn't
   case-insensitively appear anywhere in the current room's known
   `objects`/`npcs`/inventory as a new anomaly type
   (`ungrounded_command_target` or similar) in
   `anomaly_detector.py`, so Stage 1 at least surfaces it after the fact
   even without blocking it live — cheaper to build than option 1 and
   composes with bug 80's detector-generalization work.

**Effort: Medium | Risk: Medium** — option 1 changes live decide-loop
behavior (a rejected/re-prompted command changes what the agent actually
does, not just what gets logged) and needs careful scoping to avoid
false positives on legitimate but unusually-phrased commands; option 2 is
lower-risk (detection only) and could land first.

**Verification requirement (same standard as bug 80 — CLAUDE.md's "How
will we know it worked?"):** whichever direction is implemented needs a
multi-step scenario reproducing this exact shape (an object description
response immediately followed by a fabricated-object command) to prove
either the command gets rejected/flagged live (option 1) or the anomaly
appears in `detect_anomalies.py`'s output (option 2) — a single mocked
unit test on the parsing helper alone doesn't prove the decide loop
actually consults it before dispatch.

## Fix

Implemented option 1 (live self-correction inside the decide loop), not
option 2 (log-only detection) — option 2 would only have surfaced this
after the fact, not stopped the wasted turn.

`agent_tools.py` gained a grounding check that runs on every
`execute_game_command` call the model makes, before it's ever dispatched
to the game engine:

1. **Scope — object-referencing verbs only.** `_extract_grounding_checks`
   reuses `config.candidate_verbs` (via the existing
   `parse_strategies.split_verb_object`) for single-object commands
   (`examine`/`take`/`read`/`look inside`/`wear`/`push`/... — whatever the
   loaded game config actually lists), plus a small `use X on Y`/
   `cast X on Y` regex for the two-argument case. Movement, meta commands
   (`look`, `inventory`, `score`), and anything with no object-noun-phrase
   shape never enter the check at all.
2. **Two-argument commands don't conflate ground-truth sets.** For
   `use X on Y`/`cast X on Y`, `X` (the actor, typically already held) is
   checked only against inventory + spellbook; `Y` (the room-object target)
   is checked against the broader room-object set. A bare `use X`/`cast X`
   (no `on`) checks `X` against the union of both, since there's only one
   target and no second set to conflate it with.
3. **Grounding is broad and fuzzy, not strict.** `_fuzzy_object_match`
   mirrors `world_graph.resolve_room_name`'s fuzzy tier (bug 78's
   precedent — exact match, then word-set containment gated by a
   minimum-length floor), adapted for object nouns: the floor is 3 chars
   instead of room-matching's 4, since object nouns ("key", "orb") run
   shorter than room-name phrases. `examine knife` matches a known "putty
   knife"; pronoun-ish targets (`it`, `that`, `them`, ...) are skipped
   entirely rather than fuzzy-matched, since matching a pronoun against a
   name list is meaningless and would otherwise always miss (false
   nudge). A target absent from every structured ground-truth source but
   genuinely present as a substring of the raw text of the most recent
   game response is also accepted — extraction can lag/miss real objects
   (bug 77's precedent), so raw-text presence is evidence of a real
   object, not a hallucination.
4. **Ground-truth set for the *decision* is deliberately wider than the set
   shown in the *message*.** The acceptance check
   (`_room_object_candidates`) unions `state["known_entities"]`
   (cross-run pre-seeded + this-run discovered), `known_npcs`, the most
   recent game_log entry's extracted `objects`/`npcs`, and current
   inventory — not scoped to "just this room", per this bug's explicit
   bias toward permissive matching. The corrective *message* shown back to
   the model (`_build_ungrounded_nudge_message`) uses a narrower,
   room-scoped set instead (`known_entities`/`known_npcs` filtered by
   `location == current_room`, plus the last extraction and inventory) —
   telling the model "objects you can interact with right now" using a
   whole-run dump would be both noisy and actively misleading. This
   room-vs-whole-run split wasn't spelled out in the original bug write-up
   or design brief; it fell out of taking the brief's own example message
   literally (it lists only the 2 objects actually in the room, not every
   object ever seen).
5. **Reuses the existing nudge mechanism, no new retry plumbing.**
   `_run_decide_loop`'s tool-call-cap nudge (`_NUDGE_MESSAGE`,
   `tool_trace.append({"tool": "_nudge", ...})`) already had the shape
   needed: intercept a terminal `execute_game_command` call, replace its
   pending `tool_result` content with a corrective message instead of
   ending the step, and let the model call a tool again within the same
   step's budget. The new check reuses exactly that shape — when
   `_find_ungrounded_target` flags the target, the terminal call's own
   `tool_result` content is replaced with the correction, a new
   `{"tool": "_ungrounded_target_nudge", "target": ..., "message": ...}`
   entry is appended to `tool_trace`, and `continue_with_results` is
   called to give the model another turn. **One nudge per step, not a
   retry loop**: if the model repeats (or doubles down on) an ungrounded
   target after the nudge, the second attempt is dispatched as-is rather
   than forcing a fallback — forcing `look` also wastes the exact turn
   this bug is about, and the grounding heuristic is deliberately
   permissive, not infallible, so trusting the model's second answer is
   the safer failure mode. This is a considered deviation from mirroring
   the cap-nudge's "force fallback if ignored" behavior, not an oversight.
6. **Message wording explicitly forbids invention, not just implies it via
   the list** (per an explicit refinement during implementation): e.g.
   `"'sword' isn't a known object here. Objects you can actually interact
   with right now: hooded cloak, putty knife. Use these exact names —
   don't invent new object names."` The "held" variant (for `use X on Y`'s
   actor side) uses the equivalent wording against inventory/spellbook.
7. **Legacy path untouched**, per design constraint — `agent.py`'s
   `determine_next_action` builds its own commands from
   `config.candidate_verbs`/`known_entities` already; it has no equivalent
   "freely choose any target" failure mode, so nothing there needed
   changing.

## How we know it worked

**Unit tests** (`tests/test_agent_tools.py`, `TestFuzzyObjectMatch`/
`TestExtractGroundingChecks`/`TestFindUngroundedTarget`/
`TestBuildUngroundedNudgeMessage`): exact match, fuzzy substring/word-set
match (`"knife"` → `"putty knife"`), a genuine hallucination
(`"sword"` against `["putty knife", "hooded cloak"]`), a raw-text-only
match (object mentioned in the response but not yet in any structured
field), movement/meta commands never checked, pronouns never flagged,
`use X on Y`'s two ground-truth sets kept separate, and the nudge
message's candidate list scoped to the current room rather than the whole
run.

**Behavior-level test** (`TestUngroundedTargetNudgeBehavior` in the same
file), using the existing `_StubToolAdapter` canned-tool-call-sequence
fixture: reproduces this bug's exact original scenario two ways —
`test_hallucinated_object_is_nudged_not_dispatched` scripts the model
hallucinating `"examine sword"` after seeing the putty knife's "rusty and
blunt" description, then correcting itself to `"examine putty knife"`
after the nudge, and asserts (a) `_run_game_command` is called exactly
once, with the *corrected* command, never the hallucinated one — the "one
step, one real game command" invariant holds; (b) the `game_log` entry's
`tool_trace` contains exactly one `_ungrounded_target_nudge` entry naming
`"sword"`. `test_grounded_command_dispatched_without_nudge` is the
negative case: a legitimately fuzzy-matched command (`"examine knife"`)
dispatches immediately with no nudge at all, proving the fix doesn't
false-positive on real objects.

**Live re-run against a real model** (`@pytest.mark.llm`,
`test_ungrounded_target_nudge_survives_real_tool_calling_round_trip`,
DeepSeek `deepseek-chat`, 3 scripted steps replaying the bug's exact
turn-by-turn context — room description → "examine putty knife" →
the putty knife's own "rusty and blunt" description as step 3's
input): confirmed to reproduce the *actual* hallucination live, not just
in the mocked tests — one run had the model call
`execute_game_command` with `"EXAMINE SWORD"` (matching the bug's
original wording almost verbatim) after step 3's putty-knife description,
which the fix caught (`_ungrounded_target_nudge` fired with
`target: "SWORD"`) and the model corrected to `"EXAMINE PUTTY KNIFE"`,
which is what was actually dispatched. Another run had it hallucinate
`"rusty dagger"` instead, caught and corrected to `"examine putty knife"`
the same way. A separate manual live check (not part of the automated
suite, done during implementation) drove a real DeepSeek adapter through
`_run_decide_loop`'s exact protocol — forcing a corrective
`tool_result` onto a real `tool_use` id and calling
`continue_with_results` — to confirm the message-replacement mechanism
itself round-trips cleanly through the real Anthropic-shaped tool-use
protocol, independent of whether that particular run happened to
hallucinate. Total live API spend for all verification during this fix
(automated `@pytest.mark.llm` test run several times plus manual
exploratory checks): under $0.05 (DeepSeek `deepseek-chat` pricing,
roughly 30-40 short tool-calling turns).

**What to watch on a real run going forward:** in `game_log` entries
produced by the tool-calling path, `tool_trace` may now contain a
`_ungrounded_target_nudge` entry (`target`, `message`) whenever this
fires — visible in the same place the existing tool-call-cap `_nudge`
entry already is. The dispatched `action` for that step should be the
model's post-nudge choice, never the original ungrounded target named in
the nudge entry.
