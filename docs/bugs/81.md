# Bug 81: Tool-calling model hallucinates an object name and sends it as a live game command

**Status:** Open

Found while re-examining the same run documented in bug 80
(`logs/knight_orc_run_20260709_2242.json`) — the same 14-step GUI session
against a cloud tool-calling model. This is a different mechanism from
bug 80's alternation-detector gap, so it's filed separately, though both
came from the same degraded episode.

At step 9, `examine putty knife` returned: *"It is rusty and blunt,
barely able to carve slime off a puddle."* At step 10, the model called
`execute_game_command` with `"examine sword"`, stating its own reason
as: *"The game just described a rusty, blunt sword — I should examine it
properly."*

There is no sword anywhere in this scenario — `objects` at every point in
this sequence was only ever `["putty knife", "hooded cloak"]` (confirmed
by re-reading the full `extracted` field for every step in this room).
The model took the putty knife's own description ("rusty and blunt") and
misattributed it to an invented object it decided to call "sword," then
issued a real command against the live game for that nonexistent object.
The game engine rejected it (*"the word 'sword' is not needed to finish
this part of the game"*), so no state corruption resulted, but a turn was
wasted and — more importantly — this is a case of the tool-calling decide
loop sending an **ungrounded, hallucinated target** to
`execute_game_command`, not just a misclassified extraction field.

**Root cause (mechanism, not yet a full fix design):** `execute_game_command`'s
`command` field (`agent_tools.py:115-125`, `TOOL_SCHEMAS`) is an
unconstrained free-text string — the tool schema places no validation on
it, and `_dispatch_tool`/`_run_decide_loop` pass whatever the model
supplies straight to `game_engine.execute_game_command` with no check
against `known_entities`, the current room's extracted `objects`, or any
other ground-truth object list. This is the same *category* of gap bug
77 closed for **extraction** fields (`objects`/`npcs` grounded against
the raw response text) and bug 78 closed for **room naming**
(`room_quote` grounded as a verbatim substring) — but neither of those
fixes touches the tool-calling loop's own **action selection**, which
remains fully ungrounded. A model can ask the game to interact with
literally anything it imagines, not just misreport what it saw.

**Relationship to bug 80:** bug 80 is about the anomaly-detector layer
being structurally unable to flag the *alternation* this episode also
exhibits (streak-only detection logic). This bug is about a distinct,
earlier-in-the-pipeline problem — the decide loop itself producing an
ungrounded command in the first place. Fixing bug 80's detectors would
make a *future* recurrence of this kind of episode more likely to be
flagged after the fact; it would not stop the hallucinated command from
being sent. The two are complementary, not duplicates.

**Proposed fix directions (not yet designed):**
1. Ground `execute_game_command`'s target the same way bug 77 grounds
   extraction: before dispatch, if the command references an object name
   (e.g. via a lightweight `examine|take|read|...` + noun-phrase parse),
   check it against `state["known_entities"]`/the current room's last
   known `objects` list, and either reject/re-prompt the model
   ("`sword` isn't a known object here — did you mean `putty knife`?")
   or at minimum flag it (`notable_events`/a new anomaly type) so it's
   visible without silently letting it through to the game engine.
2. Alternatively (lighter-weight, no command-parsing needed): log every
   `execute_game_command` call whose target string doesn't
   case-insensitively appear anywhere in the current room's known
   `objects`/`npcs`/inventory as a new anomaly type
   (`ungrounded_command_target` or similar) in
   `anomaly_detector.py`, so Stage 1 at least surfaces it after the fact
   even without blocking it live — cheaper to build than option 1 and
   composes with bug 80's detector-generalization work.

**Effort: Medium | Risk: Medium** — option 1 changes live decide-loop
behavior (a rejected/re-prompted command changes what the agent actually
does, not just what gets logged) and needs careful scoping to avoid
false positives on legitimate but unusually-phrased commands; option 2 is
lower-risk (detection only) and could land first.

**Verification requirement (same standard as bug 80 — CLAUDE.md's "How
will we know it worked?"):** whichever direction is implemented needs a
multi-step scenario reproducing this exact shape (an object description
response immediately followed by a fabricated-object command) to prove
either the command gets rejected/flagged live (option 1) or the anomaly
appears in `detect_anomalies.py`'s output (option 2) — a single mocked
unit test on the parsing helper alone doesn't prove the decide loop
actually consults it before dispatch.
