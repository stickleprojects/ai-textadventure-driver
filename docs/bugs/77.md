# Bug 77: `objects`/`npcs` have no grounding against the raw response text

**Status:** Fixed

Same failure class as bugs 74/76 (room and exit hallucination), applied to
`parse_game_response`'s `objects`/`npcs` lists — nothing checks that an
item or character the model reports was actually mentioned in the
response before it gets written into `state["known_entities"]`/
`state["known_npcs"]` and queued for inspection.

Weaker fix than the room case, worth being explicit about: a room
description is a long, distinctive sentence, so "is this text present" is
a strong test. `"sword"` or `"orc"` are short, generic words that could
coincidentally appear in unrelated flavor text, so a substring check
catches an egregious full-phrase invention but won't reliably catch a
plausible common noun slipped in. Applied anyway, since partial protection
against a real, evidenced failure class is still better than none, and it
costs nothing (no new LLM call, purely a filter on the host side).

**Fix:** `_apply_parse_game_response` now drops any `objects`/`npcs` entry
whose name doesn't appear (case-insensitive substring) in the raw response
text, before it's written into `known_entities`/`known_npcs`.

**How we know it worked:** a synthetic `objects: ["putty knife", "invented
sword"]` against a response that only mentions "putty knife" results in
only "putty knife" being added to `known_entities` — "invented sword" is
dropped.
