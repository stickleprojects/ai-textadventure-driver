# Bug 67: Fixer-agent dev loop crashes on an unrecognized tool call

**Status:** Fixed

During iteration 3/5 of a `scripts/agent_dev_loop.py` run (investigating a
minor `empty_llm_extraction` finding), the fixer agent (`claude-sonnet-5`)
called a tool named `str_replace_based_edit_tool` — Anthropic's built-in
text-editor tool, heavily reinforced in Claude's training via harnesses
like Claude Code — instead of the harness's custom `edit_file` tool.
`run_fixer_agent()`'s dispatch loop had no guard for an unrecognized tool
name:

```python
result = _DISPATCH[block.name](block.input)
```

`_DISPATCH` only registered `bash`, `read_file`, `edit_file`, `write_file`,
so this raised an unhandled `KeyError` and crashed the entire dev-loop
process, discarding the two prior iterations' progress in that run (they
had already been applied to the working tree, so no code was lost — but
the loop itself died instead of continuing to iteration 4/5).

```
File "scripts/agent_dev_loop.py", line 307, in run_fixer_agent
    result = _DISPATCH[block.name](block.input)
KeyError: 'str_replace_based_edit_tool'
```

While fixing this, we found (and fixed) two more spots in the same function
that were one unhandled exception away from the same failure mode: a
`client.messages.create()` call with no exception handling at all, and a
`bash` tool implementation that didn't catch `subprocess.TimeoutExpired`.
Both would have crashed the whole `--iterations N` run the same way, just
from a different trigger (a transient API error, or a hung shell command).

**Fix:**
- Replaced the custom `read_file`/`edit_file`/`write_file` tool trio with
  Anthropic's real `text_editor_20250728` tool (`str_replace_based_edit_tool`)
  — schema-less, so no `input_schema` is declared; Claude already knows its
  `view`/`create`/`str_replace`/`insert` commands from training. This closes
  the root cause: the fixer model no longer needs to remember a bespoke tool
  name, since the one it reaches for by default is now the one that's
  registered. `bash` is unchanged.
- Added `_resolve_in_project()` so all text-editor paths are confined to
  `PROJECT_ROOT` (rejects `..`/symlink/absolute-path escapes), per the
  security guidance for this tool.
- `run_fixer_agent()`'s dispatch now guards the `_DISPATCH` lookup with
  `.get()` — an unrecognized tool name returns a `tool_result` with
  `is_error: true` (naming the available tools) instead of raising, so a
  future tool-name mismatch lets the model self-correct instead of crashing
  the whole run.
- `_bash()` now catches `subprocess.TimeoutExpired` and returns it as a
  normal tool error string instead of letting it propagate.
- `client.messages.create()`, the tool-dispatch call, and an unexpected
  `stop_reason` (previously silently printed to stderr and swallowed, which
  hid failures rather than surfacing them) all now raise a new
  `FixerAgentError` carrying the message transcript so far. Both call sites
  (the anomaly loop in `main()` and `run_spec_target()`) catch it — and any
  other exception, as a backstop — and call the new `_log_fixer_failure()`,
  which writes a timestamped `logs/fixer_failure_<timestamp>.log` with the
  exception type/message, `status_code`/`request_id`/`type` if present, the
  full chained traceback, and the serialized transcript of what the fixer
  agent was doing right before it broke. `sys.exit()` then points at that
  file instead of dumping a bare traceback, so a `--iterations N` run that
  dies at iteration 3 leaves a self-contained artifact for diagnosis instead
  of just a dead process and a scrollback.

**How we know it worked:** `python -m pytest tests/ -x -q
--ignore=tests/test_evals.py` passes unchanged (344 passed, 2 xfailed).
Behaviorally, a live re-run of `agent_dev_loop.py` should show the fixer
agent issuing `str_replace_based_edit_tool` calls in the `[fixer] ...`
trace instead of `edit_file`/`read_file`/`write_file`; if a future model
version calls a different, still-unregistered tool name, the trace should
show an `ERROR: unknown tool '...'` result fed back to the model rather
than the process exiting with a traceback. Verified the failure path
directly (mocking `client.messages.create` to raise) — `run_fixer_agent()`
raised `FixerAgentError` with the root API error chained via `__cause__`,
and `_log_fixer_failure()` wrote a log to `logs/` containing both the
chained traceback and the transcript. On any future fixer-agent crash, look
for the most recent `logs/fixer_failure_*.log` first — it's the diagnostic
that was previously unavailable.
