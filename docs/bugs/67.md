# Bug 67: Unrecognized take-failure aborts the rest of the object's inspection sequence

**Status:** Open

Discovered live: the agent walks into "dismal fairground in a rowan
coppice" on every run (confirmed across dozens of logs from 2026-06-30
through 2026-07-04), correctly extracts `"flagpole"` as an object every
time, but only ever *examined* it once — 2026-07-01
(`logs/watch_20260701_083519.json`), which is also the only time it
successfully took the `halyard` fastened to it (revealed by that one
`examine`). Every other run — before and after that date — never gets
past the very first interaction.

**Mechanism**, traced through `logs/watch_20260704_223723.json` (step
19-21):

1. `determine_next_action` (`agent.py:284-295`) pops a newly-discovered
   object from `uninspected_objects` and always tries `take <object>`
   *first*, unconditionally — before `candidate_verbs`' own ordering
   (`examine, take, read, ...`) applies to anything. It pre-builds the
   rest of the sequence (`post_take_verbs` — everything except `take`,
   so `examine` would run next) into `state["current_inspection"]`,
   ready to continue on the next call.
2. `take flagpole` → `"That's too heavy."` — matches neither
   `hard_failure_patterns` nor `soft_failure_patterns`, and extraction
   correctly shows `added_to_inventory: []`.
3. That is exactly the "unrecognized failure" case added in feature
   59/PR #72 (`agent.py::process_agent_step`): it sets
   `state["recheck_inventory"] = True` **and clears**
   `current_inspection["target"]`/`step_index"]` — the same clearing a
   genuine hard/soft failure does.
4. Because that clearing happens before the next decision cycle, the
   `examine flagpole → read → look inside → ...` sequence queued up in
   step 1 never runs — not even once. The agent does the forced
   `inventory` check instead, then falls through to exploration (which
   prioritizes reaching *unvisited* rooms over revisiting a known one —
   `determine_next_action` tiers 7-8), and never returns.

**Why it worked exactly once, before this fix existed:** prior to PR #72,
an unrecognized response like `"That's too heavy."` fell into the old
`else` branch and was wrongly recorded as `"succeeded"` — which, unlike
today's code, did *not* clear `current_inspection`. So the sequence
continued to `examine flagpole` next, which is how the halyard got
revealed and taken. That was masking a different bug (silently believing
an untaken item was taken, with no inventory verification), but it had
the side effect of letting the follow-through inspection continue.

**Net effect:** PR #72 correctly stops the agent from believing `take`
succeeded when it didn't, but as a side effect it also aborts the *rest*
of that object's inspection sequence on the very first unrecognized
response. Since `uninspected_objects`/`current_inspection` don't persist
cross-run, and exploration doesn't prioritize returning to already-visited
rooms, an object like the flagpole — genuinely un-takeable, but with
useful information behind `examine` — becomes effectively unreachable
unless the agent happens to revisit that specific room later in the same
run's step budget.

**Not fixed here** — needs a design decision (not attempted as part of
this investigation): should an unrecognized `take` response only abort
`take` itself and still hand off to the pre-built `post_take_verbs`
sequence (so `examine` still runs), or should `recheck_inventory` forcing
an immediate `inventory` step be made to *not* clobber a still-pending
inspection target? Either changes behavior for every object, not just
this one, so it deserves its own scoped fix/review rather than a quick
patch.
