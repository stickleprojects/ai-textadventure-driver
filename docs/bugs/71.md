# Bug 71: `agent_dev_loop.py` doesn't handle Ctrl-C — no interrupted-run record, no diagnostic log

**Status:** Open

Pressing Ctrl-C during `run_dev_loop.sh` / `scripts/agent_dev_loop.py` just kills the process with a raw `KeyboardInterrupt` traceback. Nothing is saved to record that the loop was interrupted, unlike `scripts/watch_run.py`, which already handles this (feature 30: `except KeyboardInterrupt` saves logs, appends an `INTERRUPTED` entry, and classifies the run as `"interrupted"`).

`agent_dev_loop.py` has no `except KeyboardInterrupt` anywhere in the file (confirmed by grep — zero matches), on either loop entry point:

- The anomaly-based loop (`main()`, around `scripts/agent_dev_loop.py:842-886`) — interrupting during `[3/4] Fixer agent editing code...` (`run_fixer_agent`) is the most likely place to hit Ctrl-C, since it's the longest-running step and involves live file edits via the `text_editor` tool. `run_fixer_agent`'s own failure handling only catches `except Exception as e:` (line ~866) — `KeyboardInterrupt` subclasses `BaseException`, not `Exception`, so it isn't caught there either. Whatever partial edits the fixer agent had already applied are left on disk, uncommitted and unrecorded, and `_log_fixer_failure` (the diagnostic-log writer used for real fixer failures) never runs.
- The `--spec-target` loop (`run_spec_target()`, around line 755-812) — same gap, plus it may have already checked out a dedicated scenario branch (`_create_scenario_branch`) before the interrupt, which is left checked out with no PR and no note that the attempt was abandoned mid-flight.

In both cases there's no equivalent of watch_run.py's `"Run interrupted by user (Ctrl+C)."` log entry — nothing in `logs/` or `runs/` records that iteration N was cut short, so a later run (or a person) has no way to tell an interrupted attempt apart from one that silently never started.

**Proposed fix:** Add an `except KeyboardInterrupt` around each loop body (mirroring `watch_run.py`'s feature-30 handling): write a diagnostic entry (reuse or adapt `_log_fixer_failure`'s format) noting which iteration/step was interrupted, and print a clear "interrupted, partial state may be on disk" message before exiting — rather than a bare traceback. For `--spec-target`, also surface that the scenario branch is still checked out so it isn't mistaken for a clean starting state on the next invocation.

**Effort: Low | Risk: Low**
