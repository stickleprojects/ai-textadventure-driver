# Bug 80: Alternating examine/look thrash invisible to all three deterministic anomaly detectors

**Status:** Open

Observed in a live GUI run against a cloud tool-calling model
(`logs/knight_orc_run_20260709_2242.json`, 14 steps). From step 5 onward,
in the "huge pile of garbage" room, the model alternates between
`examine putty knife` and `LOOK`/`look` seven times with no progress:

```
5  examine putty knife   -> "It is rusty and blunt..."          utility: informative
6  LOOK                  -> same room description                utility: informative
7  examine putty knife   -> same response                         utility: redundant
8  look                  -> same room description                utility: informative
9  examine putty knife   -> same response                         utility: redundant
10 examine sword         -> "word 'sword' not needed..."          utility: futile
11 LOOK                  -> same room description                utility: informative
12 examine putty knife   -> same response                         utility: redundant
13 LOOK                  -> same room description                utility: informative
```

The model's own `reason` field shows it re-justifying each `LOOK` as
"getting its bearings" ("I don't know where I am", "I need to reorient
myself") immediately after a step that already resolved
`room: "huge pile of garbage"` — it isn't trusting/reusing its own
already-established position. 3 of the 4 `examine putty knife` calls are
self-labelled `utility: redundant` by `response_classification.py`
(feature 64) — the classification layer correctly recognizes the
repetition, but nothing in the tool-calling decide loop
(`agent_tools.py::_run_decide_loop`) consumes that signal to discourage
re-selecting an action just flagged as redundant.

**Confirmed all three existing deterministic detectors miss this
run**, by running `anomaly_detector.detect_anomalies()` directly against
this log:

```
3 anomalies found
 - empty_llm_extraction
 - creature_misclassified_as_object
 - inspection_failure
```

None is the alternation thrash. Root cause is structural, not a tuning
issue — every detector that could plausibly catch this requires a
**consecutive streak** of the identical thing, and a perfect two-cycle
alternation (A, B, A, B, ...) never produces one:

- `agent._detect_loop` (`agent.py:42`) flags a single action appearing
  `>= threshold` (8) times within the last `window` (10) entries. In a
  strict A/B alternation, each individual action can reach at most
  `window / 2` (5) occurrences — mathematically incapable of tripping
  regardless of casing (this is a different, independent gap from bug 73,
  which fixed case-folding for this same function but didn't change its
  streak-vs-alternation blind spot).
- `anomaly_detector._utility_streaks` (`_STREAK_THRESHOLD = 4`) flags
  `>= 4` *consecutive* entries with the same `utility` value. Here
  `utility` alternates `informative, redundant, informative, redundant, ...`
  — never four in a row.
- `anomaly_detector._productive_thrash` needs a `_THRASH_WINDOW` of 20
  steps to even activate; this run is 14 steps total, and in any case its
  room-based signal (`_norm_room`) is only populated on `LOOK`/`look`
  entries here — `examine` entries carry `room: null` in `extracted`.

**Where this could still surface today:** `scripts/llm_review.py` (Stage
1b, LLM-based log review) is designed for exactly this class of gap — its
own docstring says it looks for "repetitive patterns not caught by
exact-match detectors" — but it wasn't run for this GUI session (the GUI
doesn't write a `runs/<run_id>.json` record at all, so `detect_anomalies.py`
can't even run Stage 1 against a GUI log today; see feature 61's
follow-up note). Whether the LLM reviewer reliably catches an alternating
two-action pattern (versus the sustained single-repeat cases it's mostly
been exercised against) is untested.

**Proposed fix directions (not yet designed):**
1. Generalize the streak-based detectors to a cycle-aware check — e.g.
   flag when the last N actions are drawn from a small set (2-3 distinct
   actions) with no forward progress (no new room, no new inventory, no
   new anomaly resolved), rather than requiring one exact value to repeat
   consecutively. `_productive_thrash`'s "distinct-count-in-a-window"
   approach is the closest existing template — this needs the same idea
   applied to actions/utility instead of rooms, and at a shorter window
   than 20 so short runs aren't blind to it.
2. Feed `utility: redundant`/`futile` classifications back into the
   tool-calling decide loop itself (`agent_tools.py`) as context for the
   *next* decision — e.g. surface "you just marked this action redundant"
   in the model's context — rather than only logging it after the fact.

**Effort: Medium | Risk: Low** — new detector logic is additive
(anomaly_detector.py already has an established pattern for
window-based, non-streak detection to extend); the decide-loop feedback
direction is a separate, higher-risk change to prompt/context content
and should be scoped independently if pursued.

**Verification requirement — a single log isn't enough here, and this
bug has two separate things that each need their own proof, not one
check standing in for both.** "Thrashing is fixed" and "the anomaly
detectors will spot it (if it recurs)" are different claims — a fix to
the decide loop's behavior doesn't by itself prove the detector layer has
also been generalized, and a new detector doesn't by itself prove the
model thrashes less. Closing this bug requires **both**, verified
separately:

1. **Detector-level proof — the anomaly detectors must actually catch
   this shape.** Add a new fixture reproducing this exact alternation
   (2-cycle A/B repeat, no consecutive streak — this run's log, or a
   synthetic equivalent) as a regression test in
   `tests/test_anomaly_detector.py` (or wherever `anomaly_detector.py`'s
   existing detector tests live), asserting the new/generalized detector
   *does* fire on it. Re-run `anomaly_detector.detect_anomalies()`
   against this run's own log (`logs/knight_orc_run_20260709_2242.json`)
   the same way this bug's investigation did, and confirm the alternation
   now appears in the anomaly list — not just the 3 unrelated anomalies
   found today. Without this, there's no evidence the detector gap
   documented above (streak-only logic) has actually been closed, only
   that the underlying behavior might have changed.
2. **Behavior-level proof — evals or multi-step scenarios showing the
   agent doesn't thrash this way.** A single-step mocked test can't show
   whether the *model* stops re-choosing an already-`redundant`-flagged
   action across turns — only a multi-step run can. Use or extend
   `tests/test_simulations.py`'s pattern (scripted multi-turn game
   responses fed through the real decide loop with a real LLM call,
   `@pytest.mark.llm`, per the 2026-07-07 journal entry on bug 45) or
   `tests/spec_scenarios/`'s data-driven fixtures, built around this
   run's actual scenario (garbage-pile room, putty knife, repeated
   look/examine) so it's a direct regression check, not a generic proxy.
   If the decide-loop-feedback fix direction is the one implemented, also
   do a live re-run of this exact GUI scenario (or an equivalent scripted
   replay) and confirm the model does not re-issue `examine putty knife`
   after its own `redundant` classification.

Both of these are the concrete "how will we know it worked" for this
bug, per the project's planning standard (CLAUDE.md's "How will we know
it worked?" requirement for any change touching agent behavior) — do not
mark this bug Fixed on detector-side evidence alone, or on behavior-side
evidence alone.
