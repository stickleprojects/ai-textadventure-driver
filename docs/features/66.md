# Feature 66: GUI runs don't write `runs/<run_id>.json`, so the anomaly/architect pipeline can't see them

**Status:** Open

Fast-follow identified while investigating bug 80 (a thrash found in a
live GUI session). `scripts/watch_run.py` writes both
`logs/<run_id>.json` (the `game_log`) and `runs/<run_id>.json` (a
run-classification record — outcome, `world_graph`, `entity_verb_outcomes`,
discovery metrics, token usage) at the end of every run, and
`scripts/detect_anomalies.py` hard-requires both files to exist. `app.py`
(the Streamlit UI) never writes either file automatically — the only way
a GUI session's log ends up in `logs/` today is a user manually clicking
"Export Run Log (JSON)" and saving it there themselves, and there's no
GUI equivalent of the run record at all. Confirmed directly: a real GUI
session's manually-exported log (`logs/knight_orc_run_20260709_2242.json`)
has no matching `runs/` file, and `detect_anomalies.py` exits with
`SystemExit(2)` ("run was likely interrupted before it could write") when
pointed at it.

This means GUI sessions are structurally invisible to the dev-loop
orchestrator pipeline (`detect_anomalies.py` → `llm_review.py` →
`architect.py`) no matter how much thrashing or how many anomalies they
contain — the only way to get a GUI run into that pipeline today is to
reproduce the same scenario headless via `watch_run.py`.

Separately, `st.session_state.run_id` (added by feature 61, part 1b) is
generated on Boot but never shown anywhere in the UI — a user watching a
live session has no way to know what run ID a `logs/`/`runs/` file (once
written) would be filed under, which matters for finding it later or
handing it to `detect_anomalies.py <run_id>` by hand.

**Fix:**
1. **Extract a shared run-record builder.** `scripts/watch_run.py`'s
   `finally:` block inlines the run-record dict assembly (outcome via
   `classify_run`, `entity_verb_outcomes` from `known_entities`,
   `world_graph_record` filtering `Unknown*` nodes, `compute_playthrough_metrics`,
   token usage totals). Move this into a new `run_evaluator.build_run_record(state, run_id, findings=None)`
   function so `watch_run.py` and `app.py` share one implementation
   instead of growing two near-parallel copies (the same anti-pattern
   feature 62/63/64 already fixed once for parsing/map/classification
   logic). `watch_run.py` calls it instead of building the dict inline;
   behavior unchanged.
2. **Write `logs/<run_id>.json` and `runs/<run_id>.json` after every
   step in `app.py`**, not just at some notional "run end" — the GUI has
   no clean end-of-run signal the way `watch_run.py`'s step-count loop
   does (a user might close the tab, kill the process, or just keep
   going indefinitely). Writing both files fresh after each `_run_step()`
   call means the pipeline can be pointed at a GUI run's `run_id` at any
   time — mid-session, after a crash, or after the tab is closed —
   without needing a deliberate "end" action. This is cheap (small JSON
   writes) and idempotent (same `run_id`, freshest content each step).
3. **Merge into the cross-run strategy file exactly once, on Reset** —
   unlike the per-step log/run-record writes, `merge_run_record` *appends*
   to `run_history` unconditionally, so calling it every step would spam
   duplicate history entries for the same run. Call it once, in the
   "Reset Game & State" button handler, right before wiping
   `st.session_state.system_state` — this mirrors `watch_run.py`'s
   semantics of "at run end, merge into strategy" using Reset as the
   GUI's closest equivalent to a run boundary. Guarded naturally by
   `st.session_state.run_id` being `None` if Reset is pressed with no
   active run.
4. **Display the run ID in the sidebar** once a run is booted (e.g.
   `st.caption(f"Run ID: {st.session_state.run_id}")`), so a user
   watching a live session can see exactly what ID a `logs/`/`runs/`
   file — and any `detect_anomalies.py <run_id>` invocation — refers to.

**Out of scope:** map PNG export (`watch_run.py`'s
`save_graph_image` calls) — the GUI already renders the world graph live
via pyvis (`ui.render_graph`), so a static PNG per step adds cost with no
corresponding need. `llm_review.py`/`architect.py` themselves are
unchanged — they already work against any `run_id` with a valid
`logs/`+`runs/` pair, regardless of which script produced it.

## How will we know it worked?

- **Run a few steps in the GUI**, then check `logs/<run_id>.json` and
  `runs/<run_id>.json` both exist on disk (no manual export needed) and
  update after each step — `runs/<run_id>.json`'s `steps` field should
  match the current `game_log` length.
- **Run `python scripts/detect_anomalies.py <run_id>` against a live (or
  just-reset) GUI session's `run_id`** — it should succeed (no
  `SystemExit(2)`) and produce `runs/orchestrator/<run_id>/anomaly_report.json`,
  something that reliably failed before this change.
- **The sidebar shows "Run ID: ui_YYYYMMDD_HHMMSS"** immediately after
  clicking Boot Engine, stable across every subsequent step in that
  session (same value shown on step 10 as step 1).
- **Click Reset once** after a GUI session with at least one step —
  `configs/knight_orc_strategy.json`'s `run_history` gains exactly one
  new entry for that `run_id` (not zero, not one-per-step). Click Reset
  again immediately without booting a new run first — no duplicate entry
  is added (guarded by `run_id` already being `None`).
- Full fast suite (`pytest tests/ -m "not slow and not llm and not cloud" -q`)
  stays green; `scripts/watch_run.py`'s own behavior is unchanged (same
  `runs/<run_id>.json` shape, produced via the extracted
  `build_run_record` instead of inline code).

**Effort: Low | Risk: Low** — additive per-step disk writes plus one
function extraction; no existing behavior in `watch_run.py` or the
pipeline scripts changes shape.
