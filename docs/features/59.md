# Feature 59: Split agent/state code into reusable library vs. Knight-Orc-bespoke layers, add spec-driven tests

**Status:** Phase 1 in progress (spec-driven scenario tests + dev-loop targeting; see below). Code/spec split (items 1–2) deferred.

## Phase 1 (branch `feat/59-spec-scenario-tests`)

Scoped down from the full plan below: instead of splitting `agent.py` first,
added spec-traceable scenario fixtures on top of the existing code, then
wired `scripts/agent_dev_loop.py` to target one at a time.

- `tests/spec_scenarios/scenarios.json` (+ `fixtures.py` loader,
  `schemas/spec_scenario.schema.json`, `tests/test_spec_scenarios.py`) —
  each entry's `spec_ref` is the kebab-case slug of the
  `agent_behavior_spec.md` `### ` heading it covers (e.g. `### Locked exits
  and keys` → `locked-exits-and-keys`). Two run `mode`s: `decision` (assert
  on `determine_next_action`'s chosen action) and `step` (patch
  `execute_game_command`/`extract_knowledge`, run `process_agent_step`,
  assert on resulting state) — both reuse the exact mock pattern already in
  `tests/test_agent.py`, no `agent.py` changes needed.
- Investigation found the `unresolved_anomalies` → `active_goal` mechanism
  already generalizes across locked exits, locked containers, and spells,
  and death/pearl-room handling already exists — so those got `decision`/
  `step` fixtures that pass today (regression coverage, previously
  untraceable to the spec). NPC theft (Requirement 23), landmark/`GO TO`
  partial-block (Requirement 25), and NPC interaction verbs (Requirement
  2/21/40) got `xfail`'d fixtures — the actual punch list.
- `scripts/agent_dev_loop.py --spec-target SCENARIO_ID` hands the fixer
  agent the matching spec section + fixture, and succeeds only when the
  scenario's `xfail` is removed, its test passes, and the full suite still
  passes. See `docs/JOURNAL.md` 2026-07-04 for what motivated scoping it
  this way instead of doing the code split first.

## Original scope

`docs/agent_behavior_spec.md` was written as a Knight-Orc-specific behavior
spec, but most of its content is generic interactive-fiction behavior
(locked doors/containers, action consequences, NPC theft, landmark
discovery, death handling) — only the vocabulary is game-specific (spell
names SLOW/UNLOCK/LIGHT, "pearl room", specific failure phrases). Plan is
to refactor with that split in mind, and add spec-driven tests since runs
are being iterated on heavily and manual live-run verification doesn't scale.

## Scope

1. **Code split** — pull `agent.py`/state code apart into a reusable
   library layer (extraction schema shape, graph maintenance, the
   priority-stack decision engine, the strategy-store persistence
   mechanism) vs. a Knight-Orc-bespoke layer (verb list, failure patterns,
   creature words, spell names, room names). This builds on the
   config-driven approach from Feature 16 and should close Feature 24
   (nav/interaction commands still hardcoded in `agent.py`) as part of the
   same work, not separately.
2. **Spec doc split** — mirror the code split in
   `docs/agent_behavior_spec.md` itself: a generic IF-agent behavior doc
   plus a thin Knight-Orc vocabulary overlay, rather than one flat
   Knight-Orc-labeled doc.
3. **Spec-driven tests** — for each behavior-spec scenario, a fixture
   (extending `scripts/generate_evals.py`'s existing saved-log-based
   fixture generation, not new test infra) plus an assertion on the
   resulting extraction/state update. Goal is scenario → fixture → test
   traceability.
