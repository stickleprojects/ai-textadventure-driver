# Feature 61: Wire the Streamlit UI into the tool-calling main loop, and surface its decision detail

**Status:** Open

The new tool-calling main loop (`agent_tools.py`, `docs/agent_tools_spec.md`,
`docs/main_loop_prompt.md`) currently only runs via `scripts/watch_run.py`
(the headless CLI runner) — `app.py` (the Streamlit UI) still exclusively
drives `agent.py::process_agent_step`, the legacy priority-list path. This
was a deliberate scoping decision when the loop was implemented (`app.py`
has no `run_id` concept, which `request_capability`'s persistence needs,
and wiring it in was called out as a fast-follow rather than bundled into
that PR), not an oversight — but it means the UI currently can't run, or
show, the new decision engine at all.

Two related pieces of work:

**1. Wire `app.py` into the new loop.** Needs a `run_id` introduced into
`st.session_state` (doesn't exist today — see `app.py::init_state`), and
the same provider branching `scripts/watch_run.py` already has (local →
`process_agent_step`, everything else → `run_tool_calling_step`) applied
to both drive points in `app.py` (`Step Once` button, the auto-run loop).

**2. Surface step-by-step decision detail in the UI.** Today
`process_agent_step`'s `llm_trace` (system/user prompts + parse attempts)
is what lets the legacy path's UI show what the LLM saw and did each step.
`agent_tools.py` doesn't currently capture an equivalent trace at all — the
tool-calling episode's intermediate calls (which tools were invoked, in
what order, with what inputs, including any `forced_fallback`/nudge
events) are visible live via stderr tracing during development but nothing
is persisted to the `game_log` entry. Showing "more detail about the new
decision engine" in the UI requires extending `agent_tools.py` to capture
and store this (a `tool_trace` list on the entry, analogous to
`llm_trace`) before the UI has anything to render — this is a prerequisite
for part 2, not just a UI-side change.

**Effort: Medium | Risk: Low** — additive on both ends (new `run_id` state,
new optional trace field); doesn't change either loop's existing behavior.

---

## Implementation Plan

This plan is written for Copilot to implement. It was designed against the
current code — `app.py` (full file), `scripts/watch_run.py`'s
provider-branching block, `agent_tools.py`'s `run_tool_calling_step`/
`_run_decide_loop`/`_dispatch_tool`, `llm.py`'s tool adapters/loaders, and
`ui.py`'s log-export functions — and verified that `llm_trace` (the legacy
path's existing per-step detail field) is captured in `game_log` entries
and included in the JSON export, but is **not** rendered anywhere in the
live dashboard today (`app.py`'s "I-O Terminal" only shows `action`/
`response`). So Part 2's UI work below is net-new rendering, not wiring up
something that already displays for the legacy path.

### Part 1: Wire `app.py` into the tool-calling loop

Mirror `scripts/watch_run.py`'s branching exactly — `LLM_PROVIDER=="local"`
keeps today's behavior (`process_agent_step` + `load_llm`); every other
provider switches to `run_tool_calling_step` + the appropriate tool
adapter. No new UI toggle — this replaces the sidebar's current generic
"cloud" branch (which loads `load_cloud_llm`, a JSON-mode `CloudLLMAdapter`
only ever used for the legacy path's extraction) with tool-adapter loading,
consistent with how `watch_run.py` has no separate "cloud JSON-mode legacy"
option either.

**1a. Sidebar LLM loading** (`app.py:95-110`) — replace the `else` branch:

```python
else:
    st.info(f"Cloud LLM: **{LLM_PROVIDER}** / {LLM_MODEL}")
    cloud_model = st.text_input("Model", value=LLM_MODEL)
    cloud_key = st.text_input("API Key", value=LLM_API_KEY, type="password")
    cloud_url = st.text_input("Base URL (optional)", value=LLM_BASE_URL)
    if LLM_PROVIDER == "anthropic":
        llm = load_anthropic_tool_llm(cloud_model, cloud_key) if ANTHROPIC_AVAILABLE else None
        available = ANTHROPIC_AVAILABLE
    else:
        llm = load_openai_tool_llm(LLM_PROVIDER, cloud_model, cloud_key, cloud_url or None) if OPENAI_AVAILABLE else None
        available = OPENAI_AVAILABLE
    if not available:
        st.warning("Required cloud SDK not installed. Tool-calling LLM unavailable.")
```

Import `ANTHROPIC_AVAILABLE`, `load_anthropic_tool_llm`, `load_openai_tool_llm`
from `llm.py` alongside the existing imports (line 16). `parse_strategy` for
this branch is `LLMToolCallParseStrategy(llm)` — construct it once, same
scope as `llm` (right after the `if/else`), analogous to how `watch_run.py`
builds `parse_strategy` alongside `llm` in its own branch.

**1b. `run_id` and boot-time initial text** — `run_id` doesn't exist in
`st.session_state` today (confirmed: only `system_state`/`level9_process`).
Add it in `init_state()`:

```python
def init_state():
    if 'system_state' not in st.session_state:
        st.session_state.system_state = _make_clean_state()
    if 'level9_process' not in st.session_state:
        st.session_state.level9_process = None
    if 'run_id' not in st.session_state:
        st.session_state.run_id = None
```

Generate a fresh one in the "Boot Engine" button handler (`app.py:115-136`),
right where `level9_process` is set — same format `watch_run.py` uses
(`f"watch_{...}"`), prefixed `ui_` to distinguish UI-driven runs in
`logs`/`runs`-adjacent tooling that greps run IDs by prefix:

```python
st.session_state.run_id = f"ui_{datetime.now().strftime('%Y%m%d_%H%M%S')}"
```

The boot handler's eager `extract_knowledge(init_response, "look", llm)`
call (line 119) only makes sense for the legacy path (`llm` there is a
JSON-mode adapter) — for the tool-calling branch there is no equivalent
eager extraction (`watch_run.py` doesn't do one either: the boot text is
just handed to the first `run_tool_calling_step` call as `initial_text`,
which decides a real command before anything gets parsed). Branch the boot
handler the same way:

```python
if LLM_PROVIDER == "local":
    extracted_init = extract_knowledge(init_response, "look", llm)
    if extracted_init.get("room"):
        state["current_room"] = extracted_init["room"]
    if extracted_init.get("exits"):
        update_graph(state, state["current_room"], extracted_init["exits"], None, None)
    log_extracted = extracted_init
else:
    log_extracted = {}
st.session_state.initial_text = init_response

state["game_log"].append({
    "timestamp": datetime.now().strftime("%H:%M:%S"),
    "action": "[SYSTEM BOOT]",
    "response": init_response,
    "extracted": log_extracted,
})
```

**1c. A single `_run_step()` helper**, replacing the duplicated
`process_agent_step(state, child, llm)` calls at the two drive points
(`Step Once` button, `app.py:157-162`; auto-run loop, `app.py:231-240`):

```python
def _run_step(child):
    if LLM_PROVIDER == "local":
        process_agent_step(state, child, llm)
    else:
        step_num = len(state["game_log"]) + 1
        run_tool_calling_step(
            state, child, llm, parse_strategy, st.session_state.run_id, step_num,
            initial_text=st.session_state.get("initial_text"),
        )
```

Passing `initial_text` on every call (not just the first) is safe and
matches `watch_run.py`'s own `step_fn` exactly — `run_tool_calling_step`
only consumes it when `state.pop("_last_response", None)` is `None`, i.e.
the very first call for this boot; every call after that is a no-op for
that argument. Both drive points become `_run_step(child)` /
`_run_step(st.session_state.level9_process)`, replacing their current
direct `process_agent_step(...)` calls one-for-one.

**1d. Reset button** (`app.py:138-146`) — also clear `st.session_state.run_id`
(set to `None`) and `st.session_state.initial_text`, so a subsequent Boot
Engine press cleanly regenerates both rather than reusing a stale run_id
tied to a previous, now-discarded game_log.

No changes needed to `agent.py`, `agent_tools.py`'s decide loop, or
`parse_strategies` for Part 1 — this is purely `app.py` wiring, matching
the doc's "additive on both ends" risk assessment.

### Part 2: Tool-call trace capture + live rendering

**2a. Capture a `tool_trace` in `agent_tools.py`**

Mirror the existing `llm_trace` field's shape/lifecycle
(`agent.py`: popped from the parse result, conditionally attached to the
entry only if non-empty) with a new field built during the decide episode
itself, not the parse step — `agent_tools.py`'s `_run_decide_loop` is
where every tool call already flows through `_dispatch_tool`.

Thread a `trace` list through both:

```python
def _dispatch_tool(state, run_id, step_num, name, call_id, call_input, trace):
    """... same docstring, plus: appends {"tool", "input", "output"} to
    trace for every dispatched call."""
    if name == "query_map":
        payload = _impl_query_map(state, call_input.get("room"))
    elif name == "query_entity_history":
        payload = _impl_query_entity_history(state, call_input.get("object"))
    elif name == "request_capability":
        payload = _impl_request_capability(
            run_id, step_num, call_input.get("description", ""), call_input.get("rationale")
        )
    elif name == "write_journal":
        payload = _impl_write_journal(state, step_num, call_input.get("note", ""))
    elif name == "search_journal":
        payload = _impl_search_journal(state, call_input.get("query", ""))
    else:
        payload = {"error": f"Unknown tool: {name}"}
    trace.append({"tool": name, "input": call_input, "output": payload})
    return _tool_result(call_id, payload)
```

In `_run_decide_loop`: initialize `tool_trace = []` right after
`total_usage`, pass it to every `_dispatch_tool(...)` call, append a trace
entry for the nudge event (right where `nudged = True` is set:
`tool_trace.append({"tool": "_nudge", "message": _NUDGE_MESSAGE})`), and
return it alongside the existing 4-tuple from every return statement
(no-tool-call fallback, cap-exceeded fallback, normal terminal return) —
`_run_decide_loop` now returns
`(action_taken, action_reason, forced_fallback, total_usage, tool_trace)`.

In `run_tool_calling_step`, capture the 5th return value and attach it to
the entry the same way `forced_fallback` already is:

```python
action_taken, action_reason, forced_fallback, usage, tool_trace = _run_decide_loop(...)
...
if tool_trace:
    entry["tool_trace"] = tool_trace
```

This is additive only — every existing caller of `_run_decide_loop` is
`run_tool_calling_step` itself (grep-confirmed, no external caller), so
the signature change is contained to this one file.

**2b. Live rendering in `app.py`'s I-O Terminal**

Today each of the last 8 log entries shows only `entry['action']` and
`entry['response']` — neither `llm_trace` nor (once added) `tool_trace` is
rendered anywhere live, only in the JSON export (`ui.generate_json_log`,
confirmed by reading it — a flat `json.dumps(state["game_log"])`). Add a
collapsed `st.expander` per entry that has either field, so both paths get
the same treatment:

```python
for entry in state["game_log"][-8:]:
    st.markdown(f"**> `{entry['action']}`**")
    st.text(entry['response'])
    trace = entry.get("tool_trace") or entry.get("llm_trace")
    if trace:
        with st.expander("Decision detail", expanded=False):
            st.json(trace)
    st.divider()
```

Kept deliberately simple (raw `st.json`, no custom formatting per tool) —
a first pass that makes the data visible at all, which is the doc's
stated bar ("surface step-by-step decision detail"), not a polished
per-tool renderer. A follow-up feature can improve the presentation once
it's clear which detail is actually useful to look at live.

### How will we know it worked?

- **Part 1, local mode (regression check)**: boot the UI with no
  `LLM_PROVIDER` env var set (defaults to `local`), click Step Once a few
  times — behavior is bit-for-bit identical to before this change (same
  `process_agent_step` call, same log entries, no `tool_trace` ever
  appears).
- **Part 1, tool-calling mode (the actual feature)**: set
  `LLM_PROVIDER=anthropic` (or `deepseek`/`openai`) + `LLM_API_KEY` before
  launching `streamlit run app.py`. Boot Engine, click Step Once: the
  sidebar should show the cloud-adapter warning only if the relevant SDK
  is missing; a successful step should produce a `game_log` entry whose
  `action` is free-form command text chosen by the tool-calling decide
  loop (not one of `determine_next_action`'s fixed priority-tier outputs),
  and `st.session_state.run_id` should be a stable `ui_YYYYMMDD_HHMMSS`
  string across the whole session (same value on step 2 as step 1).
  Auto-Run should keep working identically, just driven by the new path.
- **Part 2**: on a tool-calling-mode step where the model calls
  `query_map` or `query_entity_history` before `execute_game_command`
  (visible today only via stderr tracing during development), the new
  "Decision detail" expander under that step in the I-O Terminal should
  show those calls' names/inputs/outputs. On a step where the model calls
  no non-terminal tools, no expander appears (matches `llm_trace`'s
  existing "only attach if non-empty" behavior). Trigger the tool-call-cap
  nudge (or find a captured instance in an existing `logs/*.json` from a
  past tool-calling run) and confirm the `_nudge` entry shows up in the
  expander.
- Full fast suite (`pytest tests/ -m "not slow and not llm and not cloud" -q`)
  stays green; the new `tests/test_agent_tools.py` file's tests pass
  without needing real API keys (fully mocked tool adapter + game engine).
