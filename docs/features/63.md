# Feature 63: Map/world-graph logic is trapped in `agent.py`, reached into via private access by everything that needs it

**Status:** Open

`agent.py` owns all room-resolution and world-graph logic — `update_graph`,
`_resolve_room_name`, `_canonicalize_room`, `_normalize_room`,
`_short_room_name`, `_strip_narrator_prefix`, `_base_room_name`,
`_known_exits`, `_DIRECTION_NORMALIZE`, `_DISAMBIGUATION_RE`, plus
navigation (`_nav_command`, `get_next_move_to_target`) — as private
(`_`-prefixed), agent-internal helpers. But it is no longer only the agent
that needs this: the `query_map` LLM tool (`agent_tools.py::_impl_query_map`
— the map tool built for the tool-calling loop) reads
`state["world_graph"]` directly, and `scripts/generate_map.py` (the
standalone map-generation tool) reaches straight into `agent._resolve_room_name`
— a private function — and `agent.update_graph` to rebuild a graph from a
saved log with no live agent state at all:

```python
# scripts/generate_map.py
from agent import update_graph, _resolve_room_name
```

Confirmed by grep across the whole repo (excluding tests) for `agent\._`
— every room/graph helper in `agent.py` already has at least one external
caller reaching into it as if it were public:

| Function | External callers (non-test) |
|---|---|
| `_resolve_room_name` | `parse_strategies/base.py`, `scripts/generate_map.py` |
| `_DIRECTION_NORMALIZE` | `parse_strategies/base.py` |
| `_DIRECTIONS` | `parse_strategies/base.py`, `agent_tools.py` |
| `_short_room_name` | `parse_strategies/base.py` |
| `update_graph` (public) | `parse_strategies/base.py`, `app.py`, `scripts/generate_map.py` |

This is the same shape of problem feature 62 already solved once for
parsing (`ParseStrategy`) — a piece of logic informally shared across
modules via reach-around private access, instead of living somewhere with
a real public API. `ui.py::render_graph` is a further consumer of
`state["world_graph"]` for visualization, and any future map-mutation
tool (e.g. "mark a room as visited," "merge two nodes") would need the
same resolution/canonicalization logic `agent.py` already has, privately.

**Proposed fix:** extract map/world-graph logic into its own module (e.g.
`world_graph.py`, naming to match the `parse_strategies`/`ParseStrategy`
convention if a class-based shape ends up making more sense once designed
— e.g. `MapStrategy`), with a public API:
- `resolve_room_name(graph, room_name, exits=None)`
- `update_graph(state, room_name, exits, previous_room, action)`
- `known_exits(graph, node)`
- `canonicalize_room(name)` / `normalize_room(name)`
- `nav_command(state, target, fast=True)` / `get_next_move_to_target(state, target_room)`
- the `DIRECTION_NORMALIZE` mapping and related regex constants

`agent.py`, `agent_tools.py` (the `query_map` tool, and any future
map-mutation tool), `scripts/generate_map.py`, and `ui.py` should all
import from this new module instead of reaching into `agent.py`'s private
names. `agent.py` keeps calling into it too — it just stops being the
sole owner.

**Relationship to feature 59:** feature 59 is the broader, not-yet-designed
umbrella ("split agent.py into reusable library vs. Knight-Orc-bespoke
layers") — this feature is a concrete, scoped-down first slice of it,
following the same successful pattern as feature 62's `ParseStrategy`
extraction, rather than waiting on the full plan.

## How will we know it worked?

- `scripts/generate_map.py` no longer imports a `_`-prefixed name from
  `agent.py` — its `from agent import update_graph, _resolve_room_name`
  becomes `from world_graph import update_graph, resolve_room_name` (or
  equivalent).
- `agent_tools.py`'s `query_map` tool (and any new map-mutation tool)
  imports from the new module rather than duplicating graph-traversal
  logic inline.
- `agent.py`'s `determine_next_action`/`process_agent_step` call through
  the new module's public functions instead of local private ones — a
  `grep -n "^def _resolve_room_name\|^def update_graph"` (etc.) against
  `agent.py` should come back empty.
- Full test suite passes unchanged — this is a pure code-motion refactor,
  no behavior change, so `tests/test_agent.py`'s existing
  `_resolve_room_name`/`update_graph`/`_known_exits` tests should need
  only import-path updates, not new assertions.

**Effort: Medium | Risk: Low** — mechanical extraction of well-tested,
already-isolated functions; the main work is picking the new module's
public names and updating every import site, not changing behavior.
