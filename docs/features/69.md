# Feature 69: No way to run a fixed batch of N steps, or to cancel one in progress

**Status:** Open

Today `app.py` has exactly two ways to advance the game: "Step Once"
(always exactly 1 step) and "Start/Stop Auto-Run" (runs indefinitely
until manually stopped or the engine dies). There's no middle ground —
running, say, 5 steps to check on progress means clicking "Step Once"
five separate times, and there's no dedicated way to cancel a batch once
started other than the existing Auto-Run stop toggle (which only applies
to indefinite Auto-Run, not a fixed-count batch, since no such batch
concept exists yet).

**Fix:**
1. **Replace "Step Once" with a step-count control.** Add a
   `st.number_input("Steps", min_value=1, value=1, step=1)` next to the
   button (default 1, so a bare click behaves exactly like today's "Step
   Once"). Clicking sets a new `st.session_state.steps_remaining = N`
   rather than calling `_run_step` directly.
2. **Unify the run loop around one counter.** The existing "Auto-run
   loop" at the bottom of `app.py` (`if state["is_running"]: ...
   st.rerun()`) already re-checks a flag every rerun and is how
   indefinite Auto-Run is both driven *and* already cancellable (stopping
   sets `is_running = False`, picked up on the next rerun). Extend the
   same loop to also drain `steps_remaining` one step per rerun
   (decrementing until it hits 0), so a fixed-N-step batch reuses the
   identical mechanism instead of a second, separate stepping path.
3. **One Cancel control for both.** Add a "Cancel" button, shown
   whenever `state["is_running"]` or `steps_remaining > 0`, that zeroes
   both — so a user can stop either an indefinite Auto-Run or a
   still-in-progress N-step batch the same way, addressing "cancel a
   current run" for both cases with one affordance rather than two
   separately-worded controls.
4. **Reset already clears `is_running`**; extend it to also clear
   `steps_remaining` (new session-state field), so a Reset mid-batch
   doesn't leave a stale counter that fires again after the next Boot.

No change to `_run_step`, `process_agent_step`, or `run_tool_calling_step`
— this only changes how many times, and under what stop condition, the
existing step dispatch gets called from the UI loop.

## How will we know it worked?

- **Default behavior unchanged**: with the step-count input left at its
  default (1) and clicking the step button, behavior is identical to
  today's "Step Once" — exactly one `game_log` entry appended, no
  lingering `steps_remaining`.
- **Batch behavior**: set the input to 5, click the button — the step
  count advances automatically (via the rerun loop) until 5 new
  `game_log` entries have been appended since the click, then stops on
  its own without the user clicking anything else.
- **Cancel mid-batch**: set the input to 20, click, then click Cancel
  after a few steps have run — the batch stops before reaching 20 (fewer
  than 20 new entries since the click), and `steps_remaining` reads 0
  afterward (confirm no further auto-advancing steps occur on subsequent
  reruns).
- **Cancel mid-Auto-Run**: start Auto-Run, click Cancel — `is_running`
  becomes `False` and stepping stops, same as today's "Stop Auto-Run"
  toggle already does; both entry points converge on the same stop state.
- **Reset mid-batch**: start a 10-step batch, click Reset before it
  finishes — `steps_remaining` is 0 immediately after, and re-booting
  doesn't resume the old batch.
- Full fast suite (`pytest tests/ -m "not slow and not llm and not cloud"
  -q`) stays green — this is UI-loop-control code, not covered by direct
  unit tests, so this is primarily a live-behavior check.

**Effort: Low | Risk: Low** — extends an existing rerun-driven loop
pattern already proven for Auto-Run; no new stepping mechanism.
