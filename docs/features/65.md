# Feature 65: `.env` loader should support OS keyring references for API keys

**Status:** ✅ Fixed

The current `.env` loader resolves `$VAR` / `${VAR}` from `os.environ`, but it
cannot resolve keyring-backed references like:

```env
LLM_API_KEY=keyring:deepseek,default
ANTHROPIC_API_KEY=keyring:anthropic,default
```

That caused cloud paths (e.g. `scripts/watch_run.py`) to pass literal
`keyring:...` strings or unresolved placeholders as API keys, leading to
authentication failures.

## Fix

Extended `env_utils.load_env_file()` to recognize and resolve:

- `keyring:SERVICE,USERNAME`

Behavior:

- If keyring resolves the secret, use it.
- If keyring is unavailable, the syntax is invalid, or no secret exists, keep
  the original value unchanged (same failure-tolerant behavior used for
  unresolved `$VAR` references).
- Existing environment variables still take precedence over `.env` values.

## How will we know it worked?

- `tests/test_env_utils.py` passes new keyring cases:
  - keyring reference resolves to returned secret
  - missing secret falls back to original `keyring:...` text
  - missing keyring module falls back to original `keyring:...` text
- Existing precedence behavior remains intact:
  - pre-exported env vars are not overwritten by `.env`
- `.env.example` documents the keyring syntax so runtime configuration matches
  loader behavior.
