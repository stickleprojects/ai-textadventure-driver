# Feature 62: Pluggable game-response parsing (`ParseStrategy`), decoupled from deciding

**Status:** In progress — step 1 (`parse_strategies.py`) drafted and reviewed. Steps 2-5 below not started.

## Context

The user wants to experiment with a non-LLM (deterministic) game-response
parser and asked for the code structured so they can add it as a new
strategy themselves. This is bigger than an extension point: today
`agent.py::process_agent_step` (steps 6-24) and
`agent_tools.py::_apply_parse_game_response` are two separately-maintained,
almost-but-not-quite-parallel implementations of "apply extracted
knowledge to state." Bugs 74/75/76/77 (hallucination grounding) had to be
fixed newly in `agent_tools.py` even though bug 35's near-identical fix
already existed in `agent.py` — because there was no shared code to fix
once. Unifying removes that duplication permanently: fix the shared apply
layer once, both paths benefit, including retroactively (the legacy
JSON-mode path never had bugs 74/76/77's grounding at all — it gets it for
free here).

Two scoping decisions already made:
1. **Parsing splits from deciding.** A parse strategy only turns raw game
   text into structured data; it never chooses the next command. Deciding
   stays exactly as it is today — `determine_next_action` (legacy
   priority list) or the tool-calling decide loop (`agent_tools.py`).
2. **Both paths unified under one interface** — not just the new
   tool-calling path.

A genuine simplification falls out of the split, not just extensibility:
today's tool-calling loop has an awkward one-step lag (`_pending_step`,
`finalize_pending_step`) purely because `parse_game_response` was bundled
into the same tool-calling episode as deciding. Once parsing is a
separate, host-driven step called immediately after `execute_game_command`
(same order the legacy path already uses), the lag and all its
bookkeeping goes away entirely.

## Target architecture

```
decide(state) -> (action, reason)          # unchanged: determine_next_action, or the
                                            # tool-calling decide loop minus parse_game_response
response = execute_game_command(child, action)
result = parse_strategy.parse(response, action)   # swappable, single call, no side effects
apply_parse_result(state, result, action, response, previous_room)  # shared, both paths
# utility / log entry / loop detection — unchanged, already shared logic (agent._compute_utility etc.)
```

## Steps

### 1. New module `parse_strategies.py` — drafted, not yet committed

Currently sitting as an **untracked file** in the working tree
(`parse_strategies.py`, 511 lines) — nothing imports it yet. Reviewed
line-by-line against both originals (`agent.py:533-811`,
`agent_tools.py::_apply_parse_game_response`) and it's a faithful merge:

- `ParseStrategy` — minimal interface, one method: `parse(response_text, action_taken) -> ParseResult`.
- `apply_parse_result(state, result, action_taken, response_text, previous_room)` —
  the unified state-mutation function. Correctly preserves the legacy
  path's exact take-disambiguation, hard-failure inventory suppression
  (bug 35/75), and room/exit/object/npc grounding (bugs 74/76/77) for
  both schema aliases.
- `LLMJsonModeParseStrategy(llm_instance)` — thin wrapper around
  `llm.extract_knowledge`, unchanged prompt/parsing/behavior.
- `LLMToolCallParseStrategy(tool_adapter)` — single tool-call episode,
  only `parse_game_response` registered, returns the canonical shape
  directly.
- `DeterministicParseStrategy` — **interface/skeleton only, not
  implemented.** `parse()` raises `NotImplementedError` with a docstring
  pointing at `config.hard_failure_pattern`/`soft_failure_pattern` and
  noting that game-specific patterns belong in `configs/*.json`, not
  hardcoded. This is what the user fills in.

**Known gap spotted in review:** the merged `apply_parse_result` now
queues newly-seen objects into `state["uninspected_objects"]`
unconditionally — the original `agent_tools.py::_apply_parse_game_response`
never did this (the tool-calling decide loop has no priority-queue concept
and never reads that list). Not a functional bug today — nothing consumes
the list on that path, so it's just an unused list that grows — but worth
knowing before that state field is ever surfaced in the UI (feature 61) or
read by future tool-calling decide logic, since it would appear to be a
live queue when it's actually inert on this path.

**Also worth folding in during step 3 below:** `agent_tools.py` still has
its own `_ORCHESTRATOR_DIR`/`_append_finding`/`_capability_requests_path`,
now duplicated by `parse_strategies.py`'s copy. `_append_finding` is used
for other finding types too (`capability_gap`, not just
`room_not_grounded`), so `agent_tools.py` should import and reuse
`parse_strategies.append_finding` rather than keep a second definition.

### 2. `agent.py` — not started

- Delete steps 6-24 of `process_agent_step` (`agent.py:613-760`); replace
  with a call to `apply_parse_result`.
- `process_agent_step(state, child, llm_instance, parse_strategy=None)` —
  new optional parameter, `None` defaults to
  `LLMJsonModeParseStrategy(llm_instance)`, so every existing call site
  (`app.py`, `scripts/watch_run.py`, all 47 test call sites) keeps working
  unchanged.
- `determine_next_action` — untouched.

### 3. `agent_tools.py` — not started

- Remove `parse_game_response` from `TOOL_SCHEMAS` and the tool-calling
  loop entirely (moves to `parse_strategies.py::LLMToolCallParseStrategy`).
- Remove the one-step lag machinery: `_pending_step`, `finalize_pending_step`,
  the two-phase `run_tool_calling_step` design.
- `run_tool_calling_step(state, child, tool_adapter, parse_strategy, run_id, step_num)`
  gains the `parse_strategy` parameter.
- Collapse the duplicated finding-persistence helpers (see gap noted above).

### 4. `scripts/watch_run.py` — not started

- New `PARSE_STRATEGY` env var (`"llm"` default, `"deterministic"` once
  the user's implementation exists) — orthogonal to `LLM_PROVIDER`, so
  local decide + deterministic parse becomes a fully LLM-free agent (zero
  API calls), useful as a free baseline.
- Instantiate the configured parse strategy once, pass it into
  `process_agent_step`/`run_tool_calling_step` alongside the existing
  decide-side branching.

### 5. `DeterministicParseStrategy.parse()` — user-authored, not started

Explicitly out of scope for this feature to implement — the point of
steps 1-4 is to make this pluggable, not to write it. See requirement 45
below for a gap that any interruption-aware version of this (or of the
decide loop generally) will eventually need to account for.

## What's explicitly not touched

- `app.py` — still out of scope (feature 61).
- Any anomaly-pipeline/schema files — `apply_parse_result`'s output shape
  is unchanged from today's `extracted`, so nothing downstream needs to change.
- `determine_next_action` and the tool-calling decide loop's actual
  decision logic — only what feeds them changes, not how they choose.

## Wider consideration: interruption during multi-step inspection

Spotted while reviewing this refactor, but a distinct capability gap, not
part of this feature — filed separately as **requirement 45** ("Agent
doesn't interrupt current activity for urgent in-game events"). Summary:
neither `current_inspection`'s multi-step verb sequence nor the
tool-calling decide loop currently reacts mid-sequence to events that
should override whatever's already planned — an NPC picking up or
stealing the very object being inspected, or an NPC initiating combat
requiring an immediate fight-or-flee response instead of continuing the
inspection queue. `apply_parse_result` already detects theft
(`theft_patterns`/`taken_by_npc`) and removes the item from `inventory`,
but nothing today checks whether the object `current_inspection` is still
mid-sequence on is the one that just got taken, or aborts the sequence if
so. There is no combat/attack detection at all (no
`config.combat_patterns`-equivalent, no decide-tier for it).

## How will we know it worked?

- `pytest tests/ -q --ignore=tests/test_evals.py` passes **unchanged** —
  the main correctness bar. All 47 `process_agent_step` call sites use the
  default `parse_strategy=None`, so this refactor must be behaviorally
  invisible to them.
- A live run with `PARSE_STRATEGY` unset (default) against both DeepSeek
  and Anthropic should look identical to before this change — same tool
  set minus `parse_game_response`, no `_pending_step` lag artifacts, one
  `game_log` entry per step (no more "first call produces zero entries").
- A live run with a trivial stub `DeterministicParseStrategy` (returns an
  empty `ParseResult` unconditionally, before the user writes real logic)
  should run to completion without crashing — `extracted` fields mostly
  empty in the log, `room`/`current_room` simply never update (visible
  and expected, not an error) — proving the plumbing works before any
  real parsing logic exists.
- Once the user's real deterministic strategy exists: confirm `room_quote`
  grounding/bug-74-class protection still applies to it via the shared
  `apply_parse_result` (it should be structurally impossible for *any*
  strategy to hallucinate a room past this layer, not just the LLM ones).

**Effort: Medium | Risk: Low** — additive on both ends (new `run_id`-style
optional parameter, new pluggable strategy); doesn't change either loop's
existing behavior once the default strategy is preserved.
