# Feature 62: Pluggable game-response parsing (`ParseStrategy`), decoupled from deciding

**Status:** Fixed — all 5 steps done and verified, including a real `DeterministicParseStrategy` implementation (step 5, config-driven regex, no LLM call).

## Context

The user wants to experiment with a non-LLM (deterministic) game-response
parser and asked for the code structured so they can add it as a new
strategy themselves. This is bigger than an extension point: today
`agent.py::process_agent_step` (steps 6-24) and
`agent_tools.py::_apply_parse_game_response` are two separately-maintained,
almost-but-not-quite-parallel implementations of "apply extracted
knowledge to state." Bugs 74/75/76/77 (hallucination grounding) had to be
fixed newly in `agent_tools.py` even though bug 35's near-identical fix
already existed in `agent.py` — because there was no shared code to fix
once. Unifying removes that duplication permanently: fix the shared apply
layer once, both paths benefit, including retroactively (the legacy
JSON-mode path never had bugs 74/76/77's grounding at all — it gets it for
free here).

Two scoping decisions already made:
1. **Parsing splits from deciding.** A parse strategy only turns raw game
   text into structured data; it never chooses the next command. Deciding
   stays exactly as it is today — `determine_next_action` (legacy
   priority list) or the tool-calling decide loop (`agent_tools.py`).
2. **Both paths unified under one interface** — not just the new
   tool-calling path.

A genuine simplification falls out of the split, not just extensibility:
today's tool-calling loop has an awkward one-step lag (`_pending_step`,
`finalize_pending_step`) purely because `parse_game_response` was bundled
into the same tool-calling episode as deciding. Once parsing is a
separate, host-driven step called immediately after `execute_game_command`
(same order the legacy path already uses), the lag and all its
bookkeeping goes away entirely.

## Target architecture

```
decide(state) -> (action, reason)          # unchanged: determine_next_action, or the
                                            # tool-calling decide loop minus parse_game_response
response = execute_game_command(child, action)
result = parse_strategy.parse(response, action)   # swappable, single call, no side effects
apply_parse_result(state, result, action, response, previous_room)  # shared, both paths
# utility / log entry / loop detection — unchanged, already shared logic (agent._compute_utility etc.)
```

## Steps

### 1. New package `parse_strategies/` — done

Started as a single flat module, later split into one file per strategy
(plus the shared base) so each is easy to find and the deterministic stub
isn't buried alongside the LLM-backed ones:

- `parse_strategies/base.py` — `ParseStrategy` (minimal interface, one
  method: `parse(response_text, action_taken) -> ParseResult`) and
  `apply_parse_result(state, result, action_taken, response_text, previous_room)`
  — the unified state-mutation function. Reviewed line-by-line against
  both originals (`agent.py:533-811`, `agent_tools.py::_apply_parse_game_response`);
  correctly preserves the legacy path's exact take-disambiguation,
  hard-failure inventory suppression (bug 35/75), and room/exit/object/npc
  grounding (bugs 74/76/77) for both schema aliases.
- `parse_strategies/llm_json_mode.py` — `LLMJsonModeParseStrategy(llm_instance)`,
  a thin wrapper around `llm.extract_knowledge`, unchanged prompt/parsing/behavior.
- `parse_strategies/llm_tool_call.py` — `LLMToolCallParseStrategy(tool_adapter)`,
  a single tool-call episode, only `parse_game_response` registered,
  returns the canonical shape directly.
- `parse_strategies/deterministic.py` — `DeterministicParseStrategy`,
  **interface/skeleton only, not implemented.** `parse()` raises
  `NotImplementedError` with a docstring pointing at
  `config.hard_failure_pattern`/`soft_failure_pattern` and noting that
  game-specific patterns belong in `configs/*.json`, not hardcoded. This
  is the file the user fills in — the "stub one for Python" (a plain,
  non-LLM parser), now its own dedicated file rather than a class buried
  in a larger module.
- `parse_strategies/__init__.py` re-exports everything external code
  already imports (`ParseStrategy`, `apply_parse_result`, `append_finding`,
  `split_verb_object`, and all three strategy classes), so `agent.py`'s
  `import parse_strategies` / `agent_tools.py`'s same / `scripts/watch_run.py`'s
  `from parse_strategies import ...` needed zero changes for the split.
- `tests/test_parse_strategies.py` (new) — a shared set of known-game-response
  cases (room/exits, objects/npcs, a successful take, a hard failure that
  must suppress a claimed gain) run through **each** strategy + the shared
  `apply_parse_result`, asserting identical resulting state regardless of
  which strategy produced the raw data. `LLMJsonModeParseStrategy`/
  `LLMToolCallParseStrategy` use a faked backend (no real LLM/API call —
  `tests/test_evals.py`'s `pytest.mark.llm` suite already covers real
  extraction quality) returning a known-good extraction in that strategy's
  own schema; `DeterministicParseStrategy`'s cases are `xfail` until it's
  implemented, so they'll start exercising it for free the moment it is
  (pytest reports XPASS as a nudge to remove the marks).
- Same file also adds `test_llm_json_mode_strategy_real`/
  `test_llm_tool_call_strategy_real` — the same known-game-response cases,
  but executed for real against every provider we have credentials for.
  Loads `.env` via `env_utils.load_env_file()` (same as
  `scripts/watch_run.py`), parametrized across whatever's actually
  configured (anthropic via `ANTHROPIC_API_KEY`, `LLM_PROVIDER`'s own key
  via `LLM_API_KEY` for both its tool-calling and JSON-mode forms, and the
  local llama.cpp model if its file exists) — anything unconfigured is
  skipped individually rather than failing. New `cloud` pytest marker
  (`pytest.ini`, excluded by default alongside `llm`; CI's explicit `-m`
  filter updated too) since these make real network calls and cost money.
  Running these against the real Anthropic API reproduced bug 78 live —
  see that bug's entry.

**Known gap spotted in review:** the merged `apply_parse_result` now
queues newly-seen objects into `state["uninspected_objects"]`
unconditionally — the original `agent_tools.py::_apply_parse_game_response`
never did this (the tool-calling decide loop has no priority-queue concept
and never reads that list). Not a functional bug today — nothing consumes
the list on that path, so it's just an unused list that grows — but worth
knowing before that state field is ever surfaced in the UI (feature 61) or
read by future tool-calling decide logic, since it would appear to be a
live queue when it's actually inert on this path.

**Also worth folding in during step 3 below:** `agent_tools.py` still has
its own `_ORCHESTRATOR_DIR`/`_append_finding`/`_capability_requests_path`,
now duplicated by `parse_strategies/base.py`'s copy. `_append_finding` is used
for other finding types too (`capability_gap`, not just
`room_not_grounded`), so `agent_tools.py` should import and reuse
`parse_strategies.append_finding` rather than keep a second definition.

### 2. `agent.py` — done

- Steps 6-24 of `process_agent_step` replaced with a call to
  `parse_strategies.apply_parse_result`. The pre-parse, state-driven
  verb-outcome recording (non-take insp_verb, and take disambiguation)
  stayed in `process_agent_step` rather than moving — a first attempt at
  deleting it outright broke two tests (`test_success_records_succeeded`,
  `test_soft_failure_records_blocked_does_not_clear_inspection`) that use a
  custom `current_inspection["sequence"]` verb (`"wear"`) not in
  `config.candidate_verbs`. `apply_parse_result`'s own verb-outcome
  recording only fires for verbs `split_verb_object` recognizes
  (`config.candidate_verbs`), so it can't cover an arbitrary sequence verb
  the way the state-driven `_parse_inspection_action` derivation can. Both
  now run — redundant when they agree (the common case, verified: both
  read the same response text and reach the same verdict), never
  conflicting, and the state-driven one is authoritative for this path's
  `unrecognized_failure`/log entry.
- `process_agent_step(state, child, llm_instance, parse_strategy=None)` —
  `None` defaults to `LLMJsonModeParseStrategy(llm_instance)`, so every
  existing call site (`app.py`, `scripts/watch_run.py`, all 47 test call
  sites) keeps working unchanged.
- `determine_next_action` — untouched.
- `parse_strategies.LLMJsonModeParseStrategy` calls `agent.extract_knowledge`
  (module-attribute lookup) rather than importing `extract_knowledge`
  itself — otherwise the ~47 tests that `patch("agent.extract_knowledge",
  ...)` would silently stop taking effect, since patching a name in
  `agent`'s namespace doesn't affect a separate `from llm import
  extract_knowledge` binding in `parse_strategies/llm_json_mode.py`.
- `apply_parse_result`'s returned `extracted` dict omits the
  `added_to_inventory` key entirely on a hard-failure response (rather
  than setting it to `[]`) — matches the pre-refactor legacy dict shape
  exactly, which `test_hard_failure_clears_added_to_inventory_from_log`
  asserts via a strict `not in` check.
- Two tests encoded the *absence* of bugs 74/76's grounding (mocking a
  claimed room/exits that don't literally appear in the response text) —
  exactly the retroactive fix this refactor is supposed to deliver for the
  legacy path. Updated `test_exits_still_recorded_when_room_extracted_alongside`
  and `test_room_change_tagged_productive`'s response-text fixtures to
  actually contain the claimed room/exits, preserving each test's intent
  (exits get wired / a room change is tagged productive) instead of its
  now-stale premise (ungrounded claims used to be trusted).

### 3. `agent_tools.py` — done

- Removed `parse_game_response` from `TOOL_SCHEMAS` and the decide loop
  entirely (now lives only in `parse_strategies/llm_tool_call.py::LLMToolCallParseStrategy`,
  called separately after `execute_game_command`). System prompt's numbered
  steps updated to match (no more "call parse_game_response first").
- Removed the one-step lag machinery: `_pending_step`, `finalize_pending_step`,
  the two-phase design, `_MANDATORY_FIRST_TOOL`/`_ORDERING_CORRECTION`.
  `run_tool_calling_step` is now decide → execute → parse → apply → log,
  one call in, one `game_log` entry out — `state["_last_response"]` /
  `state["_forced_fallback_notice"]` carry the only cross-call context
  needed (previously `state["_pending_step"]` carried much more).
- `run_tool_calling_step(state, child, tool_adapter, parse_strategy, run_id, step_num, initial_text=None)`
  gained the `parse_strategy` parameter.
- Collapsed the duplicated finding-persistence helpers
  (`_ORCHESTRATOR_DIR`/`_append_finding`/`_capability_requests_path`) —
  `agent_tools.py` now calls `parse_strategies.append_finding` directly.
- Token usage in the log entry is now the *sum* of the decide loop's usage
  and the parse call's usage (previously all usage came from one bundled
  episode) — `LLMToolCallParseStrategy.parse()` reports its own `_usage`,
  popped and added in rather than either being silently dropped or
  overwriting the other.

### 4. `scripts/watch_run.py` — done

- New `PARSE_STRATEGY` env var (`"llm"` default, `"deterministic"`) —
  orthogonal to `LLM_PROVIDER`. `LLM_PROVIDER=local` + `PARSE_STRATEGY=deterministic`
  skips loading the local model entirely (`llm = None`) — a genuinely
  free, zero-API-call baseline, not just a config flag with no effect.
- Instantiates the configured parse strategy once per run, passed into
  `process_agent_step`/`run_tool_calling_step` alongside the existing
  decide-side provider branching.
- Removed the `log_len_before`/"nothing to report yet, continue" special
  case and the `finalize_pending_step(state)` flush at run end — both were
  only needed for the one-step lag, which no longer exists.

### 5. `DeterministicParseStrategy.parse()` — done

Regex-based, config-driven (new `game_config.room_patterns` /
`exit_clause_patterns` / `visible_entity_patterns` / `take_confirmation_patterns`
keys — same pattern as `hard_failure_patterns`, defaults in `game_config.py`,
overrides in `configs/knight_orc.json`, both validated by
`schemas/game_config.schema.json`). Every pattern was derived from real
saved run logs (`logs/*.json`), not guessed — including two things the
patterns' own design surfaced that weren't previously handled anywhere:

- `creature_words` gained five Knight-Orc-specific NPC roles narrated as
  "the X" rather than a proper name (`gripper`, `hermit`, `innkeeper`,
  `prophet`, `valkyrie`) — found by scanning "You can see the X" phrasings
  and "the X <action verb>" narration for words not already covered.
- `agent._DIRECTION_NORMALIZE` gained `"downwards": "down"` and
  `"upwards": "up"` — the game narrates exits/movement this way
  (`"Exits lead downwards and outside."`) but the existing map only had
  the diagonal (`northeast`→`ne`) and `inside`/`outside` forms. This fixes
  the same gap for the LLM-backed strategies too, not just this one.
- Room extraction needed a *second* pattern for `"you are outside/inside X"`
  — unlike `in`/`on`/`at`/`beside` (dropped as grammatical connectors,
  matching `agent._LEADING_PREP_RE`), `outside`/`inside` are part of the
  room's identity here (`agent.py`'s own comment: "outside a cave" and
  "inside a cave" are distinct rooms) and had to stay in the captured text.

Deliberately does not implement: gift/theft narration (theft is already
handled unconditionally by `apply_parse_result`'s own `config.theft_patterns`
cross-check regardless of strategy; gifts have no pattern yet),
`learned_spells`, `anomalies`/`blocked_by`, or `notable_events` — narrative
judgment a regex can't reliably make, or already covered elsewhere.

**Verified**, not just written: parsed all 2,983 responses across every
saved log with zero exceptions, and — restricted to the ~1,400 responses
that plausibly named a room — the extracted room agreed with the room
recorded in those logs (from the LLM-backed path, at the time each log was
made) 95% of the time. Every remaining disagreement was the *old* LLM
extraction being ungrounded or inconsistent across identical repeated
input (the class of bug 74 was filed for), not a fault in this parser —
in each case the deterministic answer was the one actually grounded in the
response text. `tests/test_parse_strategies.py`'s `KNOWN_CASES` (real,
verbatim log excerpts) exercise this strategy the same as the two
LLM-backed ones; see that file's docstring.

See requirement 45 below for a gap that any interruption-aware version of
this (or of the decide loop generally) will eventually need to account for.

## What's explicitly not touched

- `app.py` — still out of scope (feature 61).
- Any anomaly-pipeline/schema files — `apply_parse_result`'s output shape
  is unchanged from today's `extracted`, so nothing downstream needs to change.
- `determine_next_action` and the tool-calling decide loop's actual
  decision logic — only what feeds them changes, not how they choose.

## Wider consideration: interruption during multi-step inspection

Spotted while reviewing this refactor, but a distinct capability gap, not
part of this feature — filed separately as **requirement 45** ("Agent
doesn't interrupt current activity for urgent in-game events"). Summary:
neither `current_inspection`'s multi-step verb sequence nor the
tool-calling decide loop currently reacts mid-sequence to events that
should override whatever's already planned — an NPC picking up or
stealing the very object being inspected, or an NPC initiating combat
requiring an immediate fight-or-flee response instead of continuing the
inspection queue. `apply_parse_result` already detects theft
(`theft_patterns`/`taken_by_npc`) and removes the item from `inventory`,
but nothing today checks whether the object `current_inspection` is still
mid-sequence on is the one that just got taken, or aborts the sequence if
so. There is no combat/attack detection at all (no
`config.combat_patterns`-equivalent, no decide-tier for it).

## How will we know it worked? — verified

- `pytest tests/ -q --ignore=tests/test_evals.py`: **392 passed** (same
  count the tool-calling-loop PR itself reported), `ruff check .` clean.
  Two test fixtures updated (see step 2) to stop asserting on
  pre-grounding behavior; no other test needed to change.
- Live 6-step run against the real game + DeepSeek
  (`logs/watch_20260709_092710.json`, `PARSE_STRATEGY` unset): 6 steps in,
  6 `game_log` entries out (no lag artifacts), no `forced_fallback`, no
  `loop_detected`, rooms resolved and exits wired correctly step to step.
  This run also surfaced bug 78 (see below) — a real finding, not a
  regression from this refactor (the mechanism it hit is unchanged from
  the pre-refactor tool-calling path).
- Trivial-stub `DeterministicParseStrategy` plumbing check (a `parse()`
  returning `{}` unconditionally), zero API calls: ran 4 steps through
  *both* `process_agent_step` (local decide) and `run_tool_calling_step`
  (decide loop driven by a fake tool adapter, no real LLM) against the
  real game engine. Both produced exactly one log entry per call, no
  crash, `extracted` fields empty, `current_room` staying `"Unknown
  Location"` throughout — exactly the expected "plumbing works, nothing
  to extract yet" outcome.
- `room_quote` grounding (bug 74) is structurally shared — both the real
  live run and the stub-strategy check went through the same
  `apply_parse_result`, so this is already confirmed for any current or
  future strategy, not just the LLM ones.

**Bug 78 filed as a side effect of the live-run verification**: the
DeepSeek run's `room_quote`s were grounded (satisfied bug 74) but overly
verbose (whole sentences instead of just the room name), which fragmented
the world graph into duplicate nodes for rooms already known under a
shorter name. Confirmed pre-existing (same `_resolve_room_name` call the
pre-refactor tool-calling path already made) — out of scope for this
feature, filed separately. The config sidecar changes that specific run
produced (`configs/knight_orc_rooms.json`, `configs/knight_orc_strategy.json`)
were reverted — verification-run noise, not intended state to persist.

**Effort: Medium | Risk: Low** — additive on both ends (new `parse_strategy`
parameter, new pluggable strategy); default-strategy behavior preserved
