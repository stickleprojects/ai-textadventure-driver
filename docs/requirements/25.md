# Requirement 25: No response to route blockages

**Status:** Fixed

The agent has no way to detect or respond to route blockages reported by the game ("You are blocked by the drawbridge"). These are distinct from hard failures on objects — the verb is valid but a specific obstacle is preventing movement.

**Proposed schema addition:** `blocked_by: [{"obstacle": "drawbridge", "blocking": "route to castle"}]`

**Agent effect:** mark the relevant graph edge as futile OR add as anomaly with `potential_solution: null`.

**Effort: Low | Risk: Low** — schema addition + one new branch in `process_agent_step`.

**Fix:** Chose the anomaly branch of the two proposed options, not
`futile_edges`. `futile_edges` permanently gives up on a direction
cross-run with no way back — right for "this direction is just a wall,"
wrong for an obstacle that might have a solution (a lever, a key, a
spell). Routing it through `unresolved_anomalies` instead means
`determine_next_action`'s existing inventory/spellbook capability matching
(the same logic that already resolves object-based anomalies like a
locked chest) picks it up for free — no new resolution logic needed, only
the extraction and the one new branch in `process_agent_step` that adds
`{"room": current_room, "reason": blocking, "potential_solution": ""}`
keyed by `obstacle`, exactly like the existing `anomalies` field's shape.
`llm.py`'s schema/prompt gained `blocked_by` with a rule distinguishing it
from a plain "you can't do that" (only fires when a specific obstacle is
named) and one worked example.

**How we know it worked:** `tests/test_agent.py::TestRouteBlockages` (3
tests) — a blockage creates the anomaly with the right shape, doesn't
clobber an existing entry for the same obstacle (e.g. if a later step's
extraction already found a `potential_solution`), and — the important
integration check — an anomaly created this way is actually picked up by
`determine_next_action`'s existing capability-matching and turned into an
`active_goal` once the agent holds the matching item, with no changes
needed to that matching logic. `python -m pytest tests/ -q
--ignore=tests/test_evals.py` — 361 passed, 2 xfailed. Behaviorally: a
future run hitting a named obstacle (not just a generic "you can't go that
way") should show `blocked_by` in that step's `extracted` field and a new
entry in `unresolved_anomalies` for the obstacle — and if the agent later
picks up an item whose name appears in a `potential_solution` extracted
for that same obstacle, it should navigate back and apply it, the same way
it already does for object-based anomalies.
